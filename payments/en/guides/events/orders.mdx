These events cover Order Mode, where each payment order has its own address, expiry, and expected amount. Read [Events overview](/payments/en/guides/events/overview) first for the envelope, deduplication, and the rules that apply to every event.

## Events on this page

| Event | What it notifies you of | When you need it |
| --- | --- | --- |
| [`payment.order.updated`](#payment-order-updated) | An order's collection result: waiting for payment, a deposit needs your action, paid in full, underpaid, expired, or money arrived after it ended. | Always — this is the event for orders. |

## `payment.order.updated`

The primary event for Order Mode, identified by `order_id`.

**Release goods or services only when `status` is `Completed`. Do not compare amounts yourself.** Completion allows a tolerance (`amount_tolerance`), so comparing the received amount against the expected amount rejects orders that Cobo considers paid in full.

### Trigger conditions

**One event per change of the order's `status`.** You also get one when `status` has not changed but a deposit needs your attention, and `notice_type` says why.

| When you receive it | `status` | `notice_type` | What to do |
| --- | --- | --- | --- |
| The order is created | `Pending` | `null` | Record the order and show the payer what to pay. |
| The **first** deposit for this order is detected | `Processing` | `null` | Update progress. Do not release goods. |
| A deposit enters `ActionRequired` | `Processing` | `PaymentUpdated` | Act on that entry's `message`. Those funds are held until you do. |
| A deposit fails | `Processing` | `PaymentFailed` | Read that entry's `failed_reason.code`. Those funds never join the order; follow your own rules for asking the payer to pay again. |
| Cumulative receipts reach the completion threshold. Overpayment also lands here; there is no `Overpaid` status | `Completed` | `null` | Release goods, using `order_id` as the idempotency key. |
| The validity period ends with completed deposits that did not reach the threshold | `Underpaid` | `null` | Handle as underpaid. Do not treat as fully paid. |
| The validity period ends with no completed deposit, or the order is canceled | `Expired` | `null` | Close the payment window. Create a new order to keep collecting. |
| The order is already final (or reaches its final status in this same event) and another deposit arrives **and clears screening** | final | `LatePaymentReceived` | Decide whether to refund or fulfil. Do not reopen the original order. |
| The order is already final and the late deposit **fails screening** | final | `PaymentFailed` | Nothing to do — those funds never arrived. |

**The final status is decided at the moment the validity period ends and is never recalculated.** So you can see `status` `Expired` with `credited_amount` `0` and a `Completed` entry in `transactions` — that money arrived after the order ended (`is_late` is `true`), so it neither decides the final status nor adds to `credited_amount`.

**Nothing fires** when the second and later deposits are detected, when a deposit enters screening, when a deposit clears screening (`credited_amount` changes without a notification), or when a late deposit has arrived but not finished screening.

| `merchant_id` | `string` | Required | The merchant ID when the order belongs to a merchant; `null` otherwise. |

| `notice_type` | `string` | Required | The deposit change this event reports:<br/>• `PaymentUpdated` — a deposit entered `ActionRequired`.<br/>• `PaymentFailed` — a deposit failed.<br/>• `LatePaymentReceived` — a late deposit cleared screening.<br/>`null` when none of these applies. `status` usually stays the same when it is set, but can change in the same event — **to tell whether the order's status changed, compare `status` alone**. |

| `requested_amount.token_id` | `string` | Required | The token ID. |
| `requested_amount.chain_id` | `string` | Required | The chain ID. |
| `credited_amount` | `object` | Required | The total received and counted towards the order; the authoritative figure for reconciling it.<br/>• **It leaves out** deposits in screening, deposits waiting on you, rejected deposits, and money that arrived after the order ended (entries with `is_late` `true`).<br/>• ⚠️ **Do not sum `transactions` yourself** — late payments make your sum too high.<br/>• ⚠️ It **includes the portion that will be split out as your fee, so it is not the merchant's credited amount**. For what each account actually received, see [Balance changes](/payments/en/guides/events/balances). |
| `credited_amount.amount` | `string` | Required | The amount, as a decimal string. |
| `credited_amount.token_id` | `string` | Required | The token ID. |
| `credited_amount.chain_id` | `string` | Required | The chain ID. |
| `outstanding_amount` | `object` | Required | **How much more the payer still owes** = `requested_amount` − `credited_amount` (`requested_amount` is called `payable_amount` in the query APIs, so this is payable minus credited).<br/>• **How to use it: when `status` is `Underpaid`, quote it to tell the payer what is left.**<br/>• ⚠️ **Do not use it to decide whether an order was underpaid**: it can still be greater than `0` when `status` is `Completed` (the order closed within `amount_tolerance`). The order is then treated as paid in full; whether to collect the difference from the payer is your decision. Rely on `status` to tell whether an order was underpaid.<br/>• It has a floor of `0` and stays `0` on overpayment, so it **never shows how much was overpaid**. |
| `outstanding_amount.amount` | `string` | Required | The amount, as a decimal string. |
| `outstanding_amount.token_id` | `string` | Required | The token ID. |
| `outstanding_amount.chain_id` | `string` | Required | The chain ID. |
| `transactions` | `array` | Required | **Every deposit associated with the order so far**, not the change since the last event; `[]` when there are none. Replace your local copy and upsert by `transaction_id`.<br/>• ⚠️ **Deposits below the dust threshold are not in the array**: the default is `0.05`, and each token's threshold is returned as `min_amount` when you register a deposit address. |
| `transactions[].transaction_id` | `string` | Required | The deposit's ID. |
| `transactions[].tx_hash` | `string` | Required | The deposit's on-chain transaction hash. |
| `transactions[].amount` | `object` | Required | The deposit's amount. |
| `transactions[].amount.amount` | `string` | Required | The amount, as a decimal string. |
| `transactions[].amount.token_id` | `string` | Required | The token ID. |
| `transactions[].amount.chain_id` | `string` | Required | The chain ID. |
| `transactions[].source_address` | `string` | Required | The payer's on-chain address; `null` when it cannot be identified. |
| `transactions[].status` | `string` | Required | The deposit's status, with the same values as a [top-up](/payments/en/guides/events/top-up#trigger-conditions):<br/>• `Detected`<br/>• `PendingScreening`<br/>• `ActionRequired`<br/>• `Completed`<br/>• `Failed` |
| `transactions[].is_late` | `boolean` | Required | `true` means the deposit arrived after the order reached a final status, so it does not count towards `credited_amount`. |
| `transactions[].screening_mode` | `string` | Required | Which screening system is handling the deposit, for reconciliation and investigation:<br/>• `CoboKyt` — Cobo's own KYT.<br/>• `IntegratedVendor` — a third-party provider integrated by Cobo.<br/>Both can require action from you, so **read `status` to know whether it is your turn**. `null` outside screening; it can also be `null` during screening, which means Cobo could not determine the provider at that moment, not that none is configured. |
| `transactions[].message` | `string` | Required | What to do when `status` is `ActionRequired`; `null` otherwise. Written for human operators — **never match on it**. The fixed strings are:<br/>• `Additional information is required…` — check the email Cobo sent to your account contact and supply what it asks for.<br/>• `A manual compliance review by your team is required…` — complete a manual compliance review in the Screening App. |
| `transactions[].failed_reason` | `object` | Required | Set when the deposit's `status` is `Failed`; `null` otherwise. |
| `transactions[].failed_reason.code` | `string` | Required | The failure code to branch on. See [Failure reasons](#failure-reasons) for the values. |
| `transactions[].failed_reason.message` | `string` | Required | An explanation for human operators. Never match on it. |
| `created_timestamp` | `integer` | Required | When the order was created, in Unix timestamp (seconds). |
| `updated_timestamp` | `integer` | Required | When the order last changed status, in Unix timestamp (seconds). New or changed deposits do not advance it, so several events with different `transactions` can share one value: **discard only events that are strictly older, never equal ones**. |

</div>

The order object itself has no `failed_reason`. An order does not fail — it expires or ends underpaid. Failures belong to individual deposits inside `transactions`.

All amounts carry at most two decimal places, with trailing zeros stripped. Expected amounts never exceed two places to begin with; on-chain receipts (`credited_amount` and each entry's `amount`) are truncated with `ROUND_DOWN`, so a payer sending `103.0305` appears as `103.03`. Completion is evaluated on the untruncated value, so `status` is unaffected.

### Failure reasons

`failed_reason.code` is what you branch on. An entry in `transactions` can carry these three. The ID to quote when you raise a case is `order_id`, not the entry's `transaction_id`.

| `code` | What happened | What to do |
| --- | --- | --- |
| `transaction.rejected_by_screening_app` | Your own compliance team rejected this deposit in the [Screening App](https://manuals.cobo.com/en/apps/screening/introduction). | Review the case there. |
| `transaction.rejected_by_compliance` | Cobo's compliance checks rejected this deposit. | Raise it with Cobo. |
| `transaction.failed` | Everything else, including an on-chain failure and a deposit reversed by a chain reorganization. | Raise a case and quote `order_id`. |
