Bulk send has two levels of events: one for the batch and one for each item in it. Subscribe to the batch event if you only need the outcome, and to the item event if you reconcile item by item. Read [Events overview](/payments/en/guides/events/overview) first for the envelope, deduplication, and the rules that apply to every event.

## `payment.bulk_send.updated`

The batch-level event, identified by `bulk_send_id`.

| `status` | What to do |
| --- | --- |
| `Pending` | Record the batch and wait. A batch can sit here for two different reasons — see [Pending can mean waiting for approval](#pending-can-mean-waiting-for-approval). |
| `Validating` | Wait. Which items will be rejected is not known yet. |
| `Transferring` | Wait. Item-by-item progress comes from the item event. |
| `Completed` | Close the batch summary. Item completion is still reported by the item event. |
| `PartiallyCompleted` | Split your handling by the two counts: `failed_item_count` is items whose funds moved, `not_executed_item_count` is items that were never submitted. |
| `Failed` | Read `failed_reason`. A whole batch only fails **before execution starts**. |

### `Pending` can mean waiting for approval

If your organization has an approval workflow enabled, a new batch enters approval before anything else happens. **The approval step produces no event, and no field distinguishes it.** A batch in `Pending` may be waiting for validation or waiting for a person, and the payload looks the same either way. A batch that stays in `Pending` for a long time is not necessarily stuck.

### Event content

Always present: `bulk_send_id`, `source_account`, `execution_mode`, `status`, `item_count`, `failed_item_count`, `not_executed_item_count`, `requested_amounts`, `completed_amounts`, `failed_amounts`, `description`, `commission_fees`, `created_timestamp`, `updated_timestamp`. `request_id` is present when you supplied one.

| Field | Description |
| --- | --- |
| `bulk_send_id` | The batch's identity. |
| `source_account` | The account the batch pays from. |
| `execution_mode` | Whether a single bad item stops the whole batch. In `Strict` mode it does. |
| `item_count` | How many items the batch contains. |
| `failed_item_count` | Items that were submitted and failed. Funds moved for these. |
| `not_executed_item_count` | Items that were never submitted. No funds moved. |
| `requested_amounts` | The total requested, grouped by token. One batch can span several tokens and chains. |
| `completed_amounts` | The total for items that completed, grouped by token. |
| `failed_amounts` | The total for items that did not succeed, grouped by token. |
| `description` | The note attached to the batch. |
| `commission_fees` | The commission Cobo charged, one entry per token. |
| `failed_reason` | Present when `status` is `Failed`. |

`failed_amounts` merges both kinds of unsuccessful item — those whose funds moved and those never submitted — into one figure per token. Use `failed_item_count` and `not_executed_item_count`, or the item events, to tell them apart.

The batch event carries **no item list**. Per-item information only arrives through the item event, and the arrival order of the two is not guaranteed.

### Failure codes

`failed_reason.code` is what you branch on. A whole batch only fails before execution starts, so these all mean no funds moved.

**Fix the items, then create a new batch**

| `code` | What happened |
| --- | --- |
| `payment.bulk_send_no_valid_items` | No item passed validation. |
| `payment.bulk_send_strict_validation_failed` | `execution_mode` is `Strict` and one or more items failed validation, so the batch stopped. |
| `payment.bulk_send_all_items_failed` | Every item failed or was never executed. The per-item reason is in the item events. |

**Fee Station could not be charged — fix that, then create a new batch**

| `code` | What happened |
| --- | --- |
| `payment.bulk_send_commission_fee_all_failed` | The commission fee could not be charged for any item. |
| `payment.bulk_send_strict_commission_fee_failed` | `execution_mode` is `Strict` and the fee failed for one or more items. |

**Nothing to fix — create a new batch**

| `code` | What happened |
| --- | --- |
| `payment.bulk_send_strict_sweep_failed` | `execution_mode` is `Strict` and one or more sweep transactions failed. |

A batch can also fail because the approval workflow rejected or revoked it. That reason is reported on the items.

## `payment.bulk_send.item.updated`

The item-level event, identified by `bulk_send_item_id`.

| `status` | Final | What to do |
| --- | --- | --- |
| `Pending` | No | Record the item. This value covers **two stages**: waiting for validation, and validated but not yet submitted. |
| `Processing` | No | The transfer has been submitted. Wait. |
| `Completed` | Yes | Save the amount and `tx_hash`, and close the item. |
| `Failed` | Yes | The transfer was submitted and failed. Locked funds were released and the fee was returned. Whether you can resend as-is depends on `failed_reason.code`. |
| `NotExecuted` | Yes | The item was never submitted and **no funds moved**. Read `failed_reason.code`: resending without fixing the cause fails again. |

The difference between `Failed` and `NotExecuted` is whether money moved. Handle them separately.

### Event content

Always present: `bulk_send_item_id`, `bulk_send_id`, `status`, `requested_amount`, `receiving_address`, `tx_hash`, `source_account`, `description`, `created_timestamp`, `updated_timestamp`. `request_id` is present when the batch had one.

| Field | Description |
| --- | --- |
| `bulk_send_item_id` | The item's identity, and the key you use to reconcile. |
| `bulk_send_id` | The batch this item belongs to. |
| `requested_amount` | The amount to send, as an asset amount. An item completes or fails as a whole, so there are no separate completed and failed amounts. |
| `receiving_address` | The recipient's address. |
| `tx_hash` | The on-chain hash. Absent when the item never reached the chain. |
| `description` | The note attached to the item. |
| `failed_reason` | Present when `status` is `Failed` or `NotExecuted`. |

### Failure codes

`failed_reason.code` is what you branch on. These are the codes an item can carry, grouped by the response each needs.

**Fix the item, then send it again in a new batch**

| `code` | What happened |
| --- | --- |
| `payment.bulk_send_invalid_address` | The receiving address is not valid. The `message` includes the address. |
| `payment.receiving_address_matches_source_address` | The receiving address is the same as the source address. |

**Do not send to this address again**

| `code` | What happened |
| --- | --- |
| `payment.address_kya_failed` | The receiving address did not pass KYA screening. The `message` includes the address. |

**Nothing is wrong with this item — a sibling stopped it**

| `code` | What happened |
| --- | --- |
| `payment.strict_mode_other_items_validation_failed` | Another item failed validation under `Strict`. Fix that item. |
| `payment.strict_mode_other_sweep_tasks_failed` | Another sweep failed under `Strict`. |
| `payment.strict_mode_other_items_commission_fee_failed` | The fee failed for another item under `Strict`. Check Fee Station. |

**Fee Station could not be charged — fix that, then send it again**

| `code` | What happened |
| --- | --- |
| `payment.bulk_send_commission_fee_charge_failed` | The Fee Station balance is insufficient. Add funds. |
| `payment.bulk_send_commission_fee_station_not_configured` | Fee Station is not configured. Configure it. |
| `payment.bulk_send_commission_fee_charge_failed_unknown` | The charge failed for another reason. Check both the configuration and the balance. |

**The batch was not approved**

| `code` | What happened |
| --- | --- |
| `payment.app_workflow_approval_rejected` | The approval workflow rejected the batch. Ask the approver why. |
| `payment.app_workflow_approval_revoked` | The approval workflow was revoked. |

**Someone on your side rejected the transfer — clear that, then send it again**

| `code` | What happened |
| --- | --- |
| `transaction.rejected_by_policy` | The transfer matched one of your own transaction policies. Adjust the policy in Cobo Portal. |
| `transaction.rejected_by_approval` | An approver in your organization rejected the transfer. Contact them. |
| `transaction.rejected_by_screening_app` | Your compliance team rejected the transfer in the [Screening App](https://manuals.cobo.com/en/apps/screening/introduction). Review the case there. |

**Nothing to fix — send it again**

| `code` | What happened |
| --- | --- |
| `payment.sweep_task_failed` | The sweep transaction that prepares the funds failed. |

**Do not retry — raise it with Cobo**

| `code` | What happened |
| --- | --- |
| `transaction.rejected_by_compliance` | Cobo's compliance checks rejected the transfer. |
| `payment.batch_payouts_execution_failed` | The transfer failed and the cause could not be classified. |
| `transaction.failed` | The reason could not be classified. Quote `bulk_send_item_id` when you raise the case. |

## Sample events

Each sample shows the `data` object only. The envelope around it is the same for every event — see [Event structure](/payments/en/guides/events/overview#event-structure).

### The batch is accepted

Record the batch and do not submit it again. Remember that `Pending` may also mean the batch is waiting for an approver.

```json
{
  "data_type": "PaymentBulkSendUpdate",
  "bulk_send_id": "bulk_001",
  "request_id": "request_bulk_001",
  "source_account": "developer",
  "execution_mode": "Loose",
  "status": "Pending",
  "item_count": 3,
  "failed_item_count": 0,
  "not_executed_item_count": 0,
  "requested_amounts": [
    { "amount": "300.00", "token_id": "ETH_USDC", "chain_id": "ETH" }
  ],
  "completed_amounts": [],
  "failed_amounts": [],
  "description": "September affiliate payouts",
  "commission_fees": [],
  "created_timestamp": 1744710000,
  "updated_timestamp": 1744710000
}
```

No funds moved. Fix the reported items and create a new batch. Which items were at fault comes from the item events.

```json
  "bulk_send_id": "bulk_003",
  "request_id": "request_bulk_003",
  "source_account": "developer",
  "execution_mode": "Strict",
  "status": "Failed",
  "item_count": 3,
  "failed_item_count": 0,
  "not_executed_item_count": 3,
  "requested_amounts": [
    { "amount": "300.00", "token_id": "ETH_USDC", "chain_id": "ETH" }
  ],
  "completed_amounts": [],
  "failed_amounts": [
    { "amount": "300.00", "token_id": "ETH_USDC", "chain_id": "ETH" }

```

### An item completed

Save the amount and `tx_hash`, and close that item against your own recipient record using `bulk_send_item_id`.

```json

  "data_type": "PaymentBulkSendItemUpdate",
  "bulk_send_item_id": "bulk_item_0001",
  "bulk_send_id": "bulk_002",
  "request_id": "request_bulk_002",
  "source_account": "developer",
  "status": "Completed",
  "requested_amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "receiving_address": "0xaffiliate001",
  "tx_hash": "0xbulkitem001",
  "description": "affiliate 001",
  "created_timestamp": 1744712000,

```

```json
  "status": "Failed",
  "requested_amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
```

### An item was never executed

**No funds moved.** Fix the cause before resending, or it fails the same way. Here the item itself was fine and was stopped by a sibling under `Strict` mode.

```json
{
  "data_type": "PaymentBulkSendItemUpdate",
  "bulk_send_item_id": "bulk_item_0003",
  "bulk_send_id": "bulk_003",
  "request_id": "request_bulk_003",
  "source_account": "developer",
  "status": "NotExecuted",
  "requested_amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "receiving_address": "0xaffiliate003",
  "tx_hash": null,
  "description": "affiliate 003",
  "failed_reason": {
    "code": "payment.strict_mode_other_items_validation_failed",
    "message": "Cannot execute bulk send item: one or more other items failed validation when 'execution_mode' is 'Strict'."
  },
  "created_timestamp": 1744714000,
  "updated_timestamp": 1744714100
}
```

### Resending failed items

There is no retry on the original batch or item. Create a new batch, or a single payout for one recipient, and keep the original `bulk_send_id` and `bulk_send_item_id` in your own records — the new event does not carry a reference back to them.

## Transaction-level detail

`payment.bulk_send.status.updated` and `payment.bulk_send.item.status.updated` return the batch's and the item's underlying transaction detail, and are documented in [Transaction-level events](/payments/en/guides/events/transaction-level#object-transaction-events).
