These events cover Top-up Mode, where each payer has a deposit address and every deposit is tracked on its own. Read [Events overview](/payments/en/guides/events/overview) first for the envelope, deduplication, and the rules that apply to every event.

## `payment.topup.updated`

The primary event for Top-up Mode. One deposit produces one object, identified by `transaction_id`.

**Credit the funds only when `status` is `Completed`.** There is no second condition.

| `status` | Final | Creditable | What to do |
| --- | --- | --- | --- |
| `Detected` | No | No | Record the incoming deposit. |
| `PendingScreening` | No | No | Wait. Compliance screening is in progress. |
| `ActionRequired` | No | No | Act. Read `message` to find out which action is needed. |
| `Completed` | Yes | Yes | Credit `amount`, using `transaction_id` as the idempotency key. |
| `Failed` | Yes | No | Read `failed_reason.code` to decide what happens next. |

Every deposit goes through screening, so there is no direct path from `Detected` to `Completed`. `ActionRequired` returns to `PendingScreening` once you have acted, and is the only state that can move backwards.

### Event content

Always present: `transaction_id`, `merchant_id`, `payer_id`, `custom_payer_id`, `status`, `amount`, `tx_hash`, `topup_address`, `source_address`, `created_timestamp`, `updated_timestamp`.

| Field | Description |
| --- | --- |
| `transaction_id` | The deposit's transaction ID, and the object's identity. Also the parameter you pass to Cobo's compliance operations. |
| `payer_id` / `custom_payer_id` | The payer identifier assigned by Cobo, and the one you assigned. |
| `amount` | An asset amount carrying `amount`, `token_id`, and `chain_id`. Present from the first event and retained even when the deposit fails, so it tells you the size of the deposit, not whether it is usable. |
| `tx_hash` | The on-chain transaction hash. Absent for internal transfers that never touch a chain. |
| `topup_address` | The deposit address that received the funds. |
| `source_address` | The on-chain sender. `null` when the chain does not expose it. |
| `screening_mode` | Present while screening is in progress. See [Screening mode](#screening-mode). |
| `message` | Present only when `status` is `ActionRequired`. Written for human operators. |
| `failed_reason` | Present only when `status` is `Failed`. Carries `code` and `message`. |

### When `status` is `ActionRequired`

Three situations share this status, and `message` is what distinguishes them. Because `message` is not safe to match on, these three cannot be routed apart automatically and need a human queue.

| What you need to do | `message` says |
| --- | --- |
| Check the email Cobo sent to your account contact, and supply the information it asks for. | `Additional information is required…Please check the email…` |
| Submit the screening result from your own KYT provider in the Screening App. | `A screening result from your own KYT provider is required…` |
| Complete a manual compliance review in the Screening App. | `A manual compliance review by your team is required…` |

To submit a screening decision, call [Submit KYT screening decision](https://www.cobo.com/developers/v2/api-references/compliance/submit-kyt-screening-decision) with the `transaction_id` from this event. Returning, quarantining, and unfreezing funds are also keyed on `transaction_id`. None of these operations accept `tx_hash`.

### Screening mode

`screening_mode` tells you which screening system is handling the deposit: `CoboKyt`, `IntegratedVendor`, or `CustomVendor`. Use it for reconciliation and investigation.

All three modes can require action from you, so `screening_mode` does not tell you whether it is your turn to act — `status` does. The field can also be absent while screening is in progress, which means Cobo could not determine the provider at that moment, not that no provider is configured.

### Failure codes

`failed_reason.code` is what you branch on. A deposit can carry these three. The ID to quote when you raise a case is `transaction_id`.

| What to do | `code` | What happened |
| --- | --- | --- |
| Review the case in the Screening App | `transaction.rejected_by_screening_app` | Your own compliance team rejected this deposit in the [Screening App](https://manuals.cobo.com/en/apps/screening/introduction). |
| Raise it with Cobo | `transaction.rejected_by_compliance` | Cobo's compliance checks rejected this deposit. |
| Raise a case, quoting the ID below | `transaction.failed` | Everything else, including an on-chain failure and a deposit reversed by a chain reorganization. |

## `payment.address.updated`

Fires when a payer's top-up address is replaced. Update the address you show that payer, and keep accepting deposits to the previous address until it stops being funded.

**Event content:**

| Field | Description |
| --- | --- |
| `payer_id` / `custom_payer_id` | The payer whose address changed. |
| `chain` | The chain the address belongs to. Only that chain's address changes. |
| `previous_address` | The address in use before the replacement. |
| `updated_address` | The address to use from now on. |

## Unexpected deposits

A deposit that does not belong to any deposit plan, or that arrives in an unsupported token, is reported as an unexpected deposit rather than as a top-up. It is credited to your developer balance, not to a payer.

| Event | Fires when |
| --- | --- |
| `payment.transaction.external.created` | An unexpected deposit is detected. |
| `payment.transaction.external.completed` | The unexpected deposit passed screening and was credited to your developer balance. |

Both carry the fields listed in [Transaction-level events](/payments/en/guides/events/transaction-level#transaction-fields). Unexpected deposits also occur in Order Mode — see [Order events](/payments/en/guides/events/orders#unexpected-deposits).

## Sample events

Each sample shows the `data` object only. The envelope around it is the same for every event — see [Event structure](/payments/en/guides/events/overview#event-structure).

### A deposit is detected

Show the deposit as in progress. Do not credit anything yet.

```json
{
  "data_type": "PaymentTopUpUpdate",
  "transaction_id": "aff0e1cb-15b2-4e1f-9b9d-a9133715986f",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "status": "Detected",
  "amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": "0xabc123",
  "topup_address": "0xtopup_addr_M1001_user_abc",
  "source_address": "0xsender001",
  "created_timestamp": 1744689000,
  "updated_timestamp": 1744689000
}
```

### Compliance screening is in progress

Keep waiting. `screening_mode` tells you which system is reviewing it, but does not mean you have anything to do.

```json
{
  "data_type": "PaymentTopUpUpdate",
  "transaction_id": "aff0e1cb-15b2-4e1f-9b9d-a9133715986f",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "status": "PendingScreening",
  "screening_mode": "IntegratedVendor",
  "amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": "0xabc123",
  "topup_address": "0xtopup_addr_M1001_user_abc",
  "source_address": "0xsender001",
  "created_timestamp": 1744689000,
  "updated_timestamp": 1744689060
}
```

### Screening needs you to act

Put the deposit in a human queue. The three possible actions are distinguished by `message` — see [When `status` is `ActionRequired`](#when-status-is-actionrequired).

```json
{
  "data_type": "PaymentTopUpUpdate",
  "transaction_id": "aff0e1cb-15b2-4e1f-9b9d-a9133715986f",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "status": "ActionRequired",
  "screening_mode": "CoboKyt",
  "amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": "0xabc123",
  "topup_address": "0xtopup_addr_M1001_user_abc",
  "source_address": "0xsender001",
  "message": "Additional information is required before these funds can be made available. Please check the email sent to your account contact.",
  "created_timestamp": 1744689000,
  "updated_timestamp": 1744689100
}
```

### The funds are available

**This is the only state you may credit.** Use `transaction_id` as the idempotency key.

```json
{
  "data_type": "PaymentTopUpUpdate",
  "transaction_id": "aff0e1cb-15b2-4e1f-9b9d-a9133715986f",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "status": "Completed",
  "amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": "0xabc123",
  "topup_address": "0xtopup_addr_M1001_user_abc",
  "source_address": "0xsender001",
  "created_timestamp": 1744689000,
  "updated_timestamp": 1744689300
}
```

### The deposit failed

Stop any automatic crediting and read `failed_reason.code`. Here Cobo's compliance checks rejected it, so do not resend — resolve it with Cobo first.

```json
{
  "data_type": "PaymentTopUpUpdate",
  "transaction_id": "aff0e1cb-15b2-4e1f-9b9d-a9133715986f",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "status": "Failed",
  "amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": "0xabc123",
  "topup_address": "0xtopup_addr_M1001_user_abc",
  "source_address": "0xsender001",
  "failed_reason": {
    "code": "transaction.rejected_by_compliance",
    "message": "Cobo's compliance checks rejected this transaction. Do not resend it — contact Cobo support to resolve the issue first."
  },
  "created_timestamp": 1744689000,
  "updated_timestamp": 1744689400
}
```

### A payer's address is replaced

Update the address you show that payer. This is a `payment.address.updated` event, not a top-up event.

```json
{
  "data_type": "PaymentAddressUpdate",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "chain": "ETH",
  "previous_address": "0xtopup_addr_M1001_user_abc",
  "updated_address": "0xtopup_addr_M1001_user_abc_new"
}
```

## Transaction-level detail

For confirmation counts, fee breakdowns, and the on-chain detail behind each deposit, subscribe to `payment.transaction.created`, `payment.transaction.completed`, and `payment.transaction.failed`. See [Transaction-level events](/payments/en/guides/events/transaction-level).

## Balance changes

`payment.account.balance.updated` reports the resulting balance movement for a token. See [Balance events](/payments/en/guides/events/balances).
