This page covers Top-up Mode: each payer has their own deposit address, and every deposit is tracked on its own. Read [Events overview](/payments/en/guides/events/overview) first for the envelope, deduplication, and the rules that apply to every event.

## Events on this page

| Event | What it notifies you of | When you need it |
| --- | --- | --- |
| [`payment.topup.updated`](#payment-topup-updated) | One deposit's whole life: detected, screened, available to credit, or failed. | Always — this is the event for top-up deposits. |
| [`payment.address.updated`](#payment-address-updated) | A payer's deposit address was replaced. | Required. Besides replacements you request yourself, **Cobo also replaces addresses on its own**, and there is no other way to learn about those. |

## `payment.topup.updated`

The main event for Top-up Mode. One deposit is one object, identified by `transaction_id`.

**Credit funds only when `status` is `Completed`.** There is no second condition.

### Trigger conditions

**One event per change of this deposit's `status`.** `Completed` and `Failed` are terminal.

| When you receive it | `status` | Creditable | What to do |
| --- | --- | --- | --- |
| The funds are detected on a deposit address | `Detected` | ❌ | Record the incoming deposit. |
| The deposit enters compliance screening | `PendingScreening` | ❌ | Wait. |
| Screening needs you to act — supply information, submit your own KYT result, or complete a manual review | `ActionRequired` | ❌ | Act on `message`. |
| Screening passed and the transaction has at least one on-chain confirmation | `Completed` | ✅ | Credit `amount`, using `transaction_id` as the idempotency key. |
| The deposit was rejected or failed | `Failed` | ❌ | Read `failed_reason.code` to decide what happens next. |

<Warning>
  **Intermediate states can be missing.** A deposit can go straight from `Detected` to `Completed` with no event for `PendingScreening` — that does not mean it skipped screening. Overwrite your local state with the `status` on each event, do not validate that a transition is legal, and do not wait for `PendingScreening` before doing anything. `ActionRequired`, which needs you to act, stays until you handle it and is never skipped.
</Warning>

### Event content

<div className="field-table">

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `data_type` | `string` | Required | Always `PaymentTopUpUpdate`. |
| `transaction_id` | `string` | Required | The deposit's ID. Use it as the idempotency key for crediting, and as the parameter for Cobo's compliance operations. |
| `merchant_id` | `string` | Required | Which merchant this deposit belongs to. |
| `payer_id` / `custom_payer_id` | `string` | Required | The payer ID assigned by Cobo, and the one you supplied when registering the deposit address. The latter is `null` if you did not supply one. |
| `status` | `string` | Required | The current status. See [Trigger conditions](#trigger-conditions) for the values. |
| `amount` | `object` | Required | The deposit's amount, token, and chain. Never changes, and is kept even when the deposit fails. |
| `tx_hash` | `string` | Required | The on-chain transaction hash. `null` for an internal Cobo transfer that never goes on-chain, and never filled in later. Do not use it as an idempotency key. |
| `topup_address` | `string` | Required | The deposit address that received the funds. Use it to look up the payer and chain. |
| `source_address` | `string` | Required | The on-chain sender, and the target if you return the funds. `null` when the chain does not identify a sender. |
| `screening_mode` | `string` | Required | Which screening system is handling this deposit: `CoboKyt`, `IntegratedVendor`, or `CustomVendor`. Use it for reconciliation and investigation.<br/>• All three can require action from you, so **read `status` to know whether it is your turn**.<br/>• It can be `null` while screening is in progress, which means Cobo could not determine the provider at that moment, not that none is configured. |
| `message` | `string` | Required | What to do when `status` is `ActionRequired`; `null` otherwise. Written for human operators — **never match on it**. The three fixed strings are:<br/>• `Additional information is required…` — check the email Cobo sent to your account contact and supply what it asks for.<br/>• `A screening result from your own KYT provider is required…` — submit your own KYT provider's result in the Screening App.<br/>• `A manual compliance review by your team is required…` — complete a manual compliance review in the Screening App. |
| `failed_reason` | `object` | Required | `{ code, message }` when `status` is `Failed`; `null` otherwise. See [Failure reasons](#failure-reasons) for the values. |
| `created_timestamp` / `updated_timestamp` | `integer` | Required | When this deposit was created and **last changed**, in Unix timestamp (seconds). They describe the object, not when this event was produced — that is the envelope's `created_timestamp`, in milliseconds. Use `updated_timestamp` to discard out-of-order events. |

</div>

To submit a screening result, call [Submit KYT screening decision](https://www.cobo.com/developers/v2/api-references/compliance/submit-kyt-screening-decision) with the `transaction_id` from this event. Returning, quarantining, and releasing funds also work by `transaction_id`; none of these operations accept `tx_hash`.

### Failure reasons

`failed_reason.code` is what you branch on. A deposit can only carry the three below. When you raise a case, quote `transaction_id`.

| `code` | What happened | What to do |
| --- | --- | --- |
| `transaction.rejected_by_screening_app` | Your own compliance team rejected this deposit in the [Screening App](https://manuals.cobo.com/en/apps/screening/introduction). | Review the case there. |
| `transaction.rejected_by_compliance` | Cobo's compliance checks rejected this deposit. | Check with Cobo. |
| `transaction.failed` | Everything else, including on-chain failures and deposits rolled back by a chain reorganization. | Raise a case and quote `transaction_id`. |

### Sample events

Each sample shows the `data` object only. The envelope around it is the same for every event — see [Event structure](/payments/en/guides/events/overview#event-structure).

#### A deposit is detected

Mark it as in progress. Do not credit anything yet.

```json
{
  "data_type": "PaymentTopUpUpdate",
  "transaction_id": "aff0e1cb-15b2-4e1f-9b9d-a9133715986f",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "status": "Detected",
  "amount": { "amount": "100", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": "0xabc123",
  "topup_address": "0xtopup_addr_M1001_user_abc",
  "source_address": "0xsender001",
  "screening_mode": null,
  "message": null,
  "failed_reason": null,
  "created_timestamp": 1744689000,
  "updated_timestamp": 1744689000
}
```

## `payment.address.updated`

Fires when a payer's deposit address is replaced. Update the address you show that payer, and keep accepting deposits on the old one while it can still receive funds.

### Address event content

<div className="field-table">

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `data_type` | `string` | Required | Always `PaymentAddressUpdate`. |
| `merchant_id` | `string` | Required | Which merchant the payer belongs to. |
| `payer_id` / `custom_payer_id` | `string` | Required | The payer whose address changed. |
| `chain` | `string` | Required | The chain the address is on. Only the address on this chain changed. |
| `previous_address` | `string` | Required | The address before the replacement. |
| `updated_address` | `string` | Required | The address to show the payer from now on. |

</div>

```json
{
  "data_type": "PaymentAddressUpdate",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "chain": "ETH",
  "previous_address": "0xtopup_addr_M1001_user_abc",
  "updated_address": "0xtopup_addr_M1001_user_abc_new"
}
```
