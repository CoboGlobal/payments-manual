This page covers Top-up Mode: each payer has their own deposit address, and every deposit is tracked on its own. Read [Events overview](/payments/en/guides/events/overview) first for the envelope, deduplication, and the rules that apply to every event.

## Events on this page

| Event | What it notifies you of | Type |
| --- | --- | --- |
| [`payment.topup.updated`](#payment-topup-updated) | A top-up's status changed: detected, in compliance screening, action required, completed, or failed. | **Standard** |
| [`payment.address.updated`](#payment-address-updated) | A payer's deposit address was replaced. Besides replacements you request, Cobo also replaces addresses on its own. | **Standard** |

## `payment.topup.updated`

The main event for Top-up Mode.

### Trigger conditions

**One event per change of this deposit's `status`.**

| Trigger condition | `status` | Creditable | What to do |
| --- | --- | --- | --- |
| The funds are detected on a deposit address | `Detected` | ❌ | Record the incoming deposit. |
| The deposit enters compliance screening | `PendingScreening` | ❌ | Wait. |
| Screening needs you to act — supply information, or complete a manual compliance review | `ActionRequired` | ❌ | Act on `message`. |
| Screening passed and the transaction has at least one on-chain confirmation | `Completed` (final) | ✅ | Credit `amount`, using `transaction_id` as the idempotency key. |
| The deposit was rejected or failed | `Failed` (final) | ❌ | Read `failed_reason.code` to decide what happens next. |

**A deposit at or below the dust threshold sends no event.** Each token's threshold is the `min_amount` returned by [Create/Get top-up address](/payments/en/api-references/payment/createget-top-up-address) or [Batch create top-up addresses](/payments/en/api-references/payment/batch-create-top-up-addresses); tokens without their own setting default to `0.05`, and an amount must exceed it.

<Warning>
  **Intermediate states can be missing.** For example, compliance screening often finishes very quickly, so a deposit can go straight from `Detected` to `Completed` with no event for `PendingScreening` — that does not mean it skipped screening.
</Warning>

### Event content

<div className="field-table">

| Field | Type | Description |
| --- | --- | --- |
| `data_type` | `string` | Always `PaymentTopUpUpdate`. |
| `transaction_id` | `string` | The deposit's ID in Cobo. |
| `merchant_id` | `string` | Which merchant this deposit belongs to. |
| `payer_id` | `string` | The payer ID assigned by Cobo. |
| `custom_payer_id` | `string` | The payer ID you supplied when registering the deposit address; `null` if you supplied none. |
| `status` | `string` | The current status; see [Trigger conditions](#trigger-conditions) for what each means:<br/>• `Detected`<br/>• `PendingScreening`<br/>• `ActionRequired`<br/>• `Completed`<br/>• `Failed` |
| `amount` | `object` | The deposit's amount. It never changes and is kept even when the deposit fails. |
| `amount.amount` | `string` | The amount. See [Amounts](/payments/en/guides/events/overview#amounts) for the format. |
| `amount.token_id` | `string` | The token ID. |
| `amount.chain_id` | `string` | The chain ID. |
| `tx_hash` | `string` | The on-chain transaction hash. |
| `topup_address` | `string` | The deposit address that received the funds. |
| `source_address` | `string` | The on-chain sender, and the target if you return the funds. |
| `screening_mode` | `string` | Which screening system is handling the deposit, for reconciliation and investigation:<br/>• `CoboKyt` — Cobo KYT.<br/>• `IntegratedVendor` — a third-party provider integrated by Cobo in the Screening App. |
| `message` | `string` | What to do when `status` is `ActionRequired`; `null` otherwise.<br/>• `Additional information is required…` — check the email Cobo sent to your account contact and supply what it asks for.<br/>• `A manual compliance review by your team is required…` — complete a manual compliance review in the Screening App. |
| `failed_reason` | `object` | Set when `status` is `Failed`; `null` otherwise. |
| `failed_reason.code` | `string` | The failure code. See [Failure reasons](#failure-reasons) for the values. |
| `failed_reason.message` | `string` | The failure reason. |
| `created_timestamp` | `integer` | When this deposit was created, in Unix timestamp (seconds). |
| `updated_timestamp` | `integer` | When this deposit last changed status, in Unix timestamp (seconds). |

</div>

### Failure reasons

| `code` | What happened | What to do |
| --- | --- | --- |
| `transaction.rejected_by_screening_app` | Your own compliance team rejected this deposit in the [Screening App](https://manuals.cobo.com/en/apps/screening/introduction). | Review the case there. |
| `transaction.rejected_by_compliance` | Cobo's compliance checks rejected this deposit. | Check with Cobo. |
| `transaction.failed` | Failed for any other reason. | Raise a case and quote `transaction_id`. |

### Sample events

Each sample shows the `data` object only. The envelope around it is the same for every event — see [Event structure](/payments/en/guides/events/overview#event-structure).

#### A deposit is detected

Mark it as in progress. Do not credit anything yet.

```json
{
  "data_type": "PaymentTopUpUpdate",
  "transaction_id": "aff0e1cb-15b2-4e1f-9b9d-a9133715986f",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "status": "Detected",
  "amount": { "amount": "100", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": "0xabc123",
  "topup_address": "0xtopup_addr_M1001_user_abc",
  "source_address": "0xsender001",
  "screening_mode": null,
  "message": null,
  "failed_reason": null,
  "created_timestamp": 1744689000,
  "updated_timestamp": 1744689000
}
```

#### Compliance screening is in progress

Keep waiting. `screening_mode` tells you which system is reviewing it, not that you need to do something.

```json
{

  "transaction_id": "aff0e1cb-15b2-4e1f-9b9d-a9133715986f",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "status": "PendingScreening",
  "amount": { "amount": "100", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": "0xabc123",
  "topup_address": "0xtopup_addr_M1001_user_abc",
  "source_address": "0xsender001",
  "screening_mode": "IntegratedVendor",
  "message": null,
  "failed_reason": null,
  "created_timestamp": 1744689000,
  "updated_timestamp": 1744689060
}
```

## `payment.address.updated`

Fires when a payer's deposit address is replaced. When you receive it, update that payer's deposit address in your system to `updated_address`.

### Address event content

<div className="field-table">

| Field | Type | Description |
| --- | --- | --- |
| `data_type` | `string` | Always `PaymentAddressUpdate`. |
| `merchant_id` | `string` | Which merchant the payer belongs to. |
| `payer_id` | `string` | The payer whose address changed, as assigned by Cobo. |
| `custom_payer_id` | `string` | The same payer's ID in your own system, `null` if you supplied none. |
| `chain` | `string` | The chain the address is on. Only the address on this chain changed. |
| `previous_address` | `string` | The address before the replacement. |
| `updated_address` | `string` | The address to show the payer from now on. |

</div>

```json
{
  "data_type": "PaymentAddressUpdate",
  "merchant_id": "M1001",
  "payer_id": "P20250619T0310056d7aa",
  "custom_payer_id": "user_abc_10001",
  "chain": "ETH",
  "previous_address": "0xtopup_addr_M1001_user_abc",
  "updated_address": "0xtopup_addr_M1001_user_abc_new"
}
```

## Advanced events

For confirmation counts, on-chain transaction fee breakdowns, and other on-chain transaction detail, subscribe to the advanced events `payment.transaction.created`, `payment.transaction.completed`, and `payment.transaction.failed`. See [Advanced events](/payments/en/guides/events/advanced).
