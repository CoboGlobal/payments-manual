These events track a refund order from creation to completion. Read [Events overview](/payments/en/guides/events/overview) first for the envelope, deduplication, and the rules that apply to every event.

## Events on this page

| Event | What it notifies you of | Type |
| --- | --- | --- |
| [`payment.refund.updated`](#payment-refund-updated) | A refund order's result: created, completed, or failed with nothing returned. | Standard |

## `payment.refund.updated`

The primary refund event, identified by `refund_id`.

### Trigger conditions

**One event per change of this refund order's `status`.** Only the three values below appear in events.

| When you receive it | `status` | What to do |
| --- | --- | --- |
| The refund order is ready to execute — created through a refund link, or by your own call to the create-refund API | `Pending` | Record the refund and wait. |
| The refund completes | `Completed` | Reconcile and close it, using `refund_id` as the idempotency key. |
| The refund fails and **nothing was returned** | `Failed` | Read `failed_reason.code` and handle it. |

### Event content

<div className="field-table">

| Field | Type | Description |
| --- | --- | --- |
| `data_type` | `string` | Always `PaymentRefundUpdate`. |
| `refund_id` | `string` | The refund order ID, and the key you use for reconciliation idempotency. |
| `order_id` | `string` | The pay-in order this refund returns funds for; `null` when the refund is not tied to an order. |
| `merchant_id` | `string` | The merchant this refund belongs to; `null` if none. |
| `status` | `string` | The current status. Only these values appear in events:<br/>• `Pending`<br/>• `Completed`<br/>• `Failed`<br/>The query APIs expose more values, so keep deserialization tolerant, but branch on these three. |
| `request_id` | `string` | The request ID you provided when creating the refund. A refund created through a refund link inherits the request ID you gave the link, or the link ID if you gave none. |
| `to_address` | `string` | Where the funds are returned. For a refund link, the payer entered this address. |
| `requested_amount` | `object` | The amount to return, matching the `payable_amount` you passed when creating the refund. A refund either fully succeeds or fully fails, so on `Completed` this is also the amount returned. |
| `requested_amount.amount` | `string` | The amount, as a decimal string. |
| `requested_amount.token_id` | `string` | The token ID. |
| `requested_amount.chain_id` | `string` | The chain ID. |
| `tx_hash` | `string` | The on-chain hash of the refund transfer. `null` before it is broadcast; on failure, `null` means it never reached the chain and a value means it did but failed. |
| `refund_type` | `string` | Which balance funds the refund:<br/>• `Merchant` — the merchant balance.<br/>• `Psp` — the developer balance. |
| `initiator` | `string` | Who started the refund, usually an API key. A refund created through a refund link inherits the API key that created the link. |
| `commission_fee` | `object` | The commission Cobo charged; `null` when none was charged. |
| `commission_fee.fee_amount` | `string` | The commission, **denominated in USD**. It is taken from Fee Station, whose balance is in USD, so it carries no token. Reversals net off, so it can be `0` or negative. |
| `failed_reason` | `object` | Set when `status` is `Failed`; `null` otherwise. |
| `failed_reason.code` | `string` | The failure code to branch on. See [Failure reasons](#failure-reasons) for the values. |
| `failed_reason.message` | `string` | An explanation for human operators. Never match on it. |
| `created_timestamp` | `integer` | When the refund order was created, in Unix timestamp (seconds). |
| `updated_timestamp` | `integer` | When the refund order last changed status, in Unix timestamp (seconds). |

</div>

### Failure reasons

`failed_reason.code` is what you branch on.

| `code` | What happened | What to do |
| --- | --- | --- |
| `transaction.rejected_by_policy` | The transfer matched one of your own transaction policies. | Update that policy in Cobo Portal, then create the refund again. |
| `transaction.rejected_by_approval` | The transfer was rejected in your organization's approval process — by an approver, or by your callback server. | Confirm the reason with them, then create the refund again. |
| `transaction.rejected_by_signer` | The transfer was declined during signing by a co-signer. | Confirm the reason with the co-signer, then create the refund again. |
| `transaction.rejected_by_screening_app` | Your compliance team rejected the transfer in the [Screening App](https://manuals.cobo.com/en/apps/screening/introduction). | Review the case there, then create the refund again. |
| `payment.refund_fee_charge_failed` | The Fee Station balance is insufficient. | Add funds, then create the refund again. |
| `payment.refund_fee_station_not_configured` | Fee Station is not configured. | Configure it, then create the refund again. |
| `payment.refund_fee_charge_failed_unknown` | The fee could not be charged for another reason. | Check the Fee Station configuration and balance, then create the refund again. |
| `payment.refund_sweep_failed` | The sweep transaction that prepares the funds failed. | Create the refund again. |
| `payment.refund_transactions_failed` | Every refund transaction failed. The per-transaction reason is in `payment.refund.status.updated`. | Read that detail before retrying. |
| `transaction.rejected_by_compliance` | Cobo's compliance checks rejected the transfer. | Do not retry. Raise it with Cobo. |
| `transaction.failed` | The reason could not be classified. | Do not retry. Raise it with Cobo, quoting `refund_id`. |

### Sample events

Each sample shows the `data` object only. The envelope around it is the same for every event — see [Event structure](/payments/en/guides/events/overview#event-structure).

#### The refund order is created

Record it and wait. Do not create a second refund for the same order.

```json
{
  "data_type": "PaymentRefundUpdate",
  "refund_id": "refund_001",
  "order_id": "order_001",
  "merchant_id": "M1001",
  "request_id": "request_refund_001",
  "to_address": "0x9876543210abcdef1234567890abcdef12345678",
  "status": "Pending",
  "requested_amount": { "amount": "100", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": null,
  "refund_type": "Merchant",
  "initiator": "api_key_abc123",
  "commission_fee": null,
  "failed_reason": null,
  "created_timestamp": 1744690400,
  "updated_timestamp": 1744690400
}
```

#### The refund completed

Reconcile and close it, using `refund_id` as the idempotency key. `requested_amount` is also what was returned.

```json
{
  "data_type": "PaymentRefundUpdate",
  "refund_id": "refund_001",
  "order_id": "order_001",
  "merchant_id": "M1001",
  "request_id": "request_refund_001",
  "to_address": "0x9876543210abcdef1234567890abcdef12345678",
  "status": "Completed",
  "requested_amount": { "amount": "100", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": "0xrefund001",
  "refund_type": "Merchant",
  "initiator": "api_key_abc123",
  "commission_fee": { "fee_amount": "0.5" },
  "failed_reason": null,
  "created_timestamp": 1744690400,
  "updated_timestamp": 1744690500
}
```

#### The refund failed

**Nothing was returned.** Here the transfer never reached the chain, so `tx_hash` is empty.

```json
{
  "data_type": "PaymentRefundUpdate",
  "refund_id": "refund_002",
  "order_id": "order_001",
  "merchant_id": "M1001",
  "request_id": "request_refund_002",
  "to_address": "0x9876543210abcdef1234567890abcdef12345678",
  "status": "Failed",
  "requested_amount": { "amount": "100", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": null,
  "refund_type": "Merchant",
  "initiator": "api_key_abc123",
  "commission_fee": null,
  "failed_reason": {
    "code": "transaction.rejected_by_policy",
    "message": "This transaction was rejected by one of your transaction policies. Please update the applicable policy in Cobo Portal before resubmitting."
  },
  "created_timestamp": 1744690600,
  "updated_timestamp": 1744690700
}
```

#### The refund failed before the transfer

The fee could not be charged. Top up Fee Station and create the refund again.

```json
{
  "data_type": "PaymentRefundUpdate",
  "refund_id": "refund_003",
  "order_id": "order_001",
  "merchant_id": "M1001",
  "request_id": "request_refund_003",
  "to_address": "0x9876543210abcdef1234567890abcdef12345678",
  "status": "Failed",
  "requested_amount": { "amount": "100", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": null,
  "refund_type": "Merchant",
  "initiator": "api_key_abc123",
  "commission_fee": null,
  "failed_reason": {
    "code": "payment.refund_fee_charge_failed",
    "message": "Cannot charge refund fee: Fee Station balance is insufficient. Please add funds to Fee Station and try again."
  },
  "created_timestamp": 1744690800,
  "updated_timestamp": 1744690900
}
```
