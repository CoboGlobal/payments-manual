These events track a refund order from creation to completion. Read [Events overview](/payments/en/guides/events/overview) first for the envelope, deduplication, and the rules that apply to every event.

Refunds currently apply to orders only. To return funds received through Top-up Mode, create a payout instead.

## `payment.refund.updated`

The primary refund event, identified by `refund_id`.

| `status` | Fires when | What to do |
| --- | --- | --- |
| `Pending` | The refund order is created through a refund link. | Record the refund and wait. |
| `Completed` | The refund completed. | Reconcile and close the refund, using `refund_id` as the idempotency key. |
| `Failed` | The refund failed and **nothing was returned**. | Read `failed_reason` and handle it. |

Only these three values reach you. The public `RefundStatus` enumeration also contains `PendingConfirmation`, `AddressPending`, `AddressSubmitted`, `Processing`, and `PartiallyCompleted`, but none of them has a send point, so no event carries them. Your SDK will still expose those values; you do not need a branch for them.

A refund either succeeds in full or fails in full. There is no partial refund outcome.

### Event content

Always present: `refund_id`, `order_id`, `merchant_id`, `request_id`, `to_address`, `status`, `requested_amount`, `tx_hash`, `refund_type`, `initiator`, `commission_fee`, `created_timestamp`, `updated_timestamp`.

| Field | Description |
| --- | --- |
| `refund_id` | The refund order's identity, and the key you use for reconciliation idempotency. |
| `order_id` | The pay-in order this refund returns funds for. |
| `request_id` | The request ID you supplied when creating the refund. |
| `to_address` | The address receiving the refund. |
| `requested_amount` | The amount to return, as an asset amount. It corresponds to the `payable_amount` you passed when creating the refund. |
| `tx_hash` | The on-chain hash of the refund transfer. Absent when the refund failed before being broadcast. |
| `refund_type` | Which balance funds the refund: `Merchant` or `Psp`. |
| `initiator` | Who initiated the refund. |
| `commission_fee` | The commission Cobo charged, as a single object carrying `token_id` and `fee_amount`. A refund involves exactly one token, so this is not an array. The value can be `0` when a fee was charged and then fully reversed, or negative when a reversal outweighs the charge. |
| `failed_reason` | Present only when `status` is `Failed`. Carries `code` and `message`. |

Because a refund has no completed or failed amount fields, `requested_amount` is both what was asked for and, once `status` is `Completed`, what was returned.

### Failure codes

`failed_reason.code` is what you branch on.

| What to do | `code` | What happened |
| --- | --- | --- |
| Clear it on your side, then create the refund again | `transaction.rejected_by_policy` | The transfer matched one of your own transaction policies. Adjust the policy in Cobo Portal. |
| Clear it on your side, then create the refund again | `transaction.rejected_by_approval` | An approver in your organization rejected the transfer. Contact them. |
| Clear it on your side, then create the refund again | `transaction.rejected_by_screening_app` | Your compliance team rejected the transfer in the [Screening App](https://manuals.cobo.com/en/apps/screening/introduction). |
| Fix Fee Station, then create the refund again | `payment.refund_fee_charge_failed` | The Fee Station balance is insufficient. Add funds. |
| Fix Fee Station, then create the refund again | `payment.refund_fee_station_not_configured` | Fee Station is not configured. Configure it. |
| Fix Fee Station, then create the refund again | `payment.refund_fee_charge_failed_unknown` | The charge failed for another reason. Check both the configuration and the balance. |
| Create the refund again as-is | `payment.refund_sweep_failed` | The sweep transaction that prepares the funds failed. |
| Read the transaction detail first | `payment.refund_transactions_failed` | Every refund transaction failed. The per-transaction reason is in `payment.refund.status.updated`. |
| Do not retry — raise it with Cobo | `transaction.rejected_by_compliance` | Cobo's compliance checks rejected the transfer. |
| Do not retry — raise it with Cobo, quoting `refund_id` | `transaction.failed` | The reason could not be classified. |

## Sample events

Each sample shows the `data` object only. The envelope around it is the same for every event — see [Event structure](/payments/en/guides/events/overview#event-structure).

### The refund order is created

Record it and wait. Do not create a second refund for the same order.

```json
{
  "data_type": "PaymentRefundUpdate",
  "refund_id": "refund_001",
  "order_id": "order_001",
  "merchant_id": "M1001",
  "request_id": "request_refund_001",
  "to_address": "0x9876543210abcdef1234567890abcdef12345678",
  "status": "Pending",
  "requested_amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": null,
  "refund_type": "Merchant",
  "initiator": "api_key_abc123",
  "commission_fee": null,
  "created_timestamp": 1744690400,
  "updated_timestamp": 1744690400
}
```

### The refund completed

Reconcile and close it, using `refund_id` as the idempotency key. `requested_amount` is also what was returned.

```json
{
  "data_type": "PaymentRefundUpdate",
  "refund_id": "refund_001",
  "order_id": "order_001",
  "merchant_id": "M1001",
  "request_id": "request_refund_001",
  "to_address": "0x9876543210abcdef1234567890abcdef12345678",
  "status": "Completed",
  "requested_amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": "0xrefund001",
  "refund_type": "Merchant",
  "initiator": "api_key_abc123",
  "commission_fee": { "token_id": "ETH_USDC", "fee_amount": "0.50" },
  "created_timestamp": 1744690400,
  "updated_timestamp": 1744690500
}
```

### The refund failed

**Nothing was returned.** Here the transfer never reached the chain, so `tx_hash` is empty.

```json
{
  "data_type": "PaymentRefundUpdate",
  "refund_id": "refund_002",
  "order_id": "order_001",
  "merchant_id": "M1001",
  "request_id": "request_refund_002",
  "to_address": "0x9876543210abcdef1234567890abcdef12345678",
  "status": "Failed",
  "requested_amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": null,
  "refund_type": "Merchant",
  "initiator": "api_key_abc123",
  "commission_fee": null,
  "failed_reason": {
    "code": "transaction.rejected_by_policy",
    "message": "This transaction was rejected by one of your transaction policies. Adjust the relevant policy in Cobo Portal, then resend."
  },
  "created_timestamp": 1744690600,
  "updated_timestamp": 1744690700
}
```

### The refund failed before the transfer

The fee could not be charged. Top up Fee Station and create the refund again.

```json
{
  "data_type": "PaymentRefundUpdate",
  "refund_id": "refund_003",
  "order_id": "order_001",
  "merchant_id": "M1001",
  "request_id": "request_refund_003",
  "to_address": "0x9876543210abcdef1234567890abcdef12345678",
  "status": "Failed",
  "requested_amount": { "amount": "100.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "tx_hash": null,
  "refund_type": "Merchant",
  "initiator": "api_key_abc123",
  "commission_fee": null,
  "failed_reason": {
    "code": "payment.refund_fee_charge_failed",
    "message": "Cannot charge refund fee: Fee Station balance is insufficient. Please add funds to Fee Station and try again."
  },
  "created_timestamp": 1744690800,
  "updated_timestamp": 1744690900
}
```

## Transaction-level detail

`payment.refund.status.updated` returns this refund's underlying transaction detail and is documented in [Transaction-level events](/payments/en/guides/events/transaction-level#object-transaction-events).
