These events track a single payout or transfer request, whether it settles in crypto or through an Off-Ramp to a bank account. Read [Events overview](/payments/en/guides/events/overview) first for the envelope, deduplication, and the rules that apply to every event.

For batch payouts, see [Bulk send events](/payments/en/guides/events/bulk-send).

## `payment.payout.updated`

The primary payout event, identified by `payout_id`.

| `status` | Final | What to do |
| --- | --- | --- |
| `Pending` | No | The request was accepted. Wait. |
| `Preparing` | No | Wait. |
| `Transferring` | No | Wait. **Do not close the payout before a final status**, even if some outgoing transactions have already completed. |
| `Completed` | Yes | Close the payout. This means Cobo completed the transfer; it does not mean the recipient's platform has credited it. |
| `PartiallyCompleted` | Yes | Create a **new** payout for the amount in `failed_amounts`. Do not resend the part that already succeeded. |
| `Failed` | Yes | Read `failed_reason` and handle it. Do not retry in place. |
| `RejectedByBank` | Yes | The receiving bank rejected the Off-Ramp transfer. Confirm the account details with the recipient first; resending unchanged is likely to be rejected again. |

### Event content

Always present: `payout_id`, `request_id`, `source_account`, `status`, `requested_amounts`, `failed_amounts`, `requested_target`, `transactions`, `actual_payout_amount`, `initiator`, `commission_fees`, `remark`, `created_timestamp`, `updated_timestamp`.

| Field | Description |
| --- | --- |
| `payout_id` | The payout's identity, and the key you use when closing the payout and when raising a support case. |
| `request_id` | The request ID you supplied when creating the payout. |
| `source_account` | The account the funds are paid from. |
| `requested_target` | Where the money is going, in business terms. Carries `target_type`, which is either `Address` — with `address` and `chain_id` — or `BankAccount` — with `bank_account_id`, `account_alias`, `bank_name`, and `currency`. It never exposes on-chain execution detail such as contract addresses. |
| `initiator` | Who initiated the payout. |
| `remark` | The note attached to the payout. |
| `transactions` | The outgoing transactions. See [Reading the transactions array](#reading-the-transactions-array). |
| `failed_reason` | Present when `status` is `Failed`, `RejectedByBank`, or `PartiallyCompleted`. |

### The amounts are on two different sides

| Field | Side | Notes |
| --- | --- | --- |
| `requested_amounts` | Source | What you asked to pay out, grouped by source token. |
| `failed_amounts` | Source | The part that was not paid out, grouped by source token. At a final status, the amount that succeeded is the difference between the two. |
| `actual_payout_amount` | Delivery | What the recipient actually received. For crypto this is in the destination token; for Off-Ramp it is in the bank account's currency. Absent until the payout finishes. |
| `commission_fees` | Source | The commission Cobo charged, one entry per token. An entry can be `0` or negative when charges and reversals offset. |

**Do not subtract across the two sides.** Cross-chain conversion and fiat settlement mean the source and delivery figures are not the same asset.

**Do not reconcile `failed_amounts` against `transactions`.** A payout item can fail before any outgoing transaction is created — during fund consolidation, cross-chain conversion, or commission collection — and in that case no entry exists in the array at all.

### Reading the transactions array

Entries use `result`, not `status`, to avoid confusion with wallet transaction states. The values are `Completed`, `Failed`, and `null`, where `null` means there is no result yet.

Each entry carries `transaction_id`, `amount`, `tx_hash`, and `result`. `tx_hash` is empty until the transaction is broadcast. An entry with `result` `Failed` carries its own `failed_reason` — see [Failure codes](#failure-codes).

After cross-chain conversion, an entry's `amount` is in the token actually sent, which can differ from the source token in `requested_amounts`.

### Failure codes

`failed_reason.code` is what you branch on. When a payout is partially completed, read the object-level `failed_reason` first — it is populated whatever stage the failure happened at, and if an outgoing transaction was the cause, the matching entry in `transactions` carries a more precise reason as well.

| What to do | `code` | What happened |
| --- | --- | --- |
| Pay the rest with a new payout | `payment.payout_partially_failed` | Some of the payout could not be completed. `failed_amounts` is the amount to send again. |
| Clear it on your side, then create the payout again | `transaction.rejected_by_policy` | The transfer matched one of your own transaction policies. Adjust the policy in Cobo Portal. |
| Clear it on your side, then create the payout again | `transaction.rejected_by_approval` | An approver in your organization rejected the transfer. Contact them. |
| Clear it on your side, then create the payout again | `transaction.rejected_by_screening_app` | Your compliance team rejected the transfer in the [Screening App](https://manuals.cobo.com/en/apps/screening/introduction). |
| Fix Fee Station, then create the payout again | `payment.payout_fee_charge_failed` | The Fee Station balance is insufficient. Add funds. |
| Fix Fee Station, then create the payout again | `payment.payout_fee_station_not_configured` | Fee Station is not configured. Configure it. |
| Fix Fee Station, then create the payout again | `payment.payout_fee_charge_failed_unknown` | The charge failed for another reason. Check both the configuration and the balance. |
| Create the payout again as-is | `payment.payout_sweep_failed` | The sweep transaction that prepares the funds failed. |
| Check the route, then create the payout again | `payment.payout_bridge_failed` | Every cross-chain transaction failed, so the assets could not be converted. |
| Read the transaction detail first | `payment.payout_transactions_failed` | Every outgoing transaction failed. The per-transaction reason is in `transactions`. |
| Check the account details with the recipient first | `transaction.rejected_by_bank` | The receiving bank returned the transfer. Off-Ramp only. Sending the same details again will most likely be rejected again. |
| Do not retry — raise it with Cobo | `transaction.rejected_by_compliance` | Cobo's compliance checks rejected the transfer. |
| Do not retry — raise it with Cobo, quoting `payout_id` | `transaction.failed` | The reason could not be classified. |

## `payment.bank_withdrawal.status.updated`

Fires when a bank withdrawal changes status. A bank withdrawal moves fiat out of one of your virtual accounts into a target bank account, and is created with [Create bank withdrawal](/payments/en/api-references/payment/create-bank-withdrawal).

| `status` | Meaning |
| --- | --- |
| `Pending` | The bank withdrawal was created and is awaiting processing. |
| `Processing` | The bank withdrawal is being processed. |
| `Completed` | The funds have left the virtual account. |
| `Failed` | The withdrawal failed. Read `failed_reason` for the cause. |

**Event content:** the `data` object carries `data_type` `PaymentBankWithdrawal`, plus:

- `bank_withdrawal_id` (required) — The bank withdrawal ID generated by Cobo.
- `request_id` (required) — The request ID you provided when creating the bank withdrawal.
- `source_bank_account_id` (required) — The ID of the source bank account, which must be a virtual account (tagged `VA`).
- `target_bank_account_id` (required) — The ID of the target bank account that receives the withdrawal.
- `source_bank_account` (required) — The full details of the source bank account.
- `target_bank_account` (required) — The full details of the target bank account.
- `currency` (required) — The fiat currency of the bank withdrawal, for example `USD`.
- `amount` (required) — The bank withdrawal amount, as a decimal string in the currency's display unit, for example `100.00`.
- `bank_tx_fee` (optional) — The bank transaction fee charged for the bank withdrawal.
- `status` (required) — The current status. One of: `Pending`, `Processing`, `Completed`, `Failed`.
- `remark` (optional) — The remark for the bank withdrawal.
- `failed_reason` (optional) — Why the bank withdrawal failed. Populated only when `status` is `Failed`.
- `timeline` (required) — The status timeline of the bank withdrawal. Each item carries a `status` and the `timestamp` at which the withdrawal entered it, in Unix timestamp (seconds).
- `created_timestamp` (required) — The creation time, in Unix timestamp (seconds).

<Note>
  The bank withdrawal payload does not carry an `updated_timestamp`. To determine when the withdrawal entered its current status, read the last entry in `timeline`.
</Note>

For full details, see [Get bank withdrawal information](/payments/en/api-references/payment/get-bank-withdrawal-by-id).

## Sample events

Each sample shows the `data` object only. The envelope around it is the same for every event — see [Event structure](/payments/en/guides/events/overview#event-structure).

### The payout is accepted

Record it and do not submit the request again. `requested_target` is your own instruction echoed back — check it against what you sent.

```json
{
  "data_type": "PaymentPayoutUpdate",
  "payout_id": "payout_001",
  "request_id": "request_payout_001",
  "source_account": "developer",
  "status": "Pending",
  "requested_amounts": [
    { "amount": "500.00", "token_id": "ETH_USDC", "chain_id": "ETH" }
  ],
  "failed_amounts": [],
  "requested_target": {
    "target_type": "Address",
    "address": "0xrecipient001",
    "chain_id": "ETH"
  },
  "transactions": [],
  "actual_payout_amount": null,
  "initiator": "api_key_abc123",
  "commission_fees": [],
  "remark": "September vendor settlement",
  "created_timestamp": 1744700000,
  "updated_timestamp": 1744700000
}
```

### The payout is partially completed

Create a **new** payout for the amount in `failed_amounts`. Do not resend the part that succeeded.

  "payout_id": "payout_002",
  "request_id": "request_payout_002",

  "requested_amounts": [
    { "amount": "500.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
    { "amount": "300.00", "token_id": "TRON_USDT", "chain_id": "TRON" }
  ],
  "failed_amounts": [
    { "amount": "300.00", "token_id": "TRON_USDT", "chain_id": "TRON" }
  ],
  "requested_target": {
    "target_type": "Address",
    "address": "0xrecipient002",
    "chain_id": "ETH"
  },
  "transactions": [
    {
      "transaction_id": "9a8b7c6d-0002-4e5f-8a9b-000000000001",
      "amount": { "amount": "500.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
      "tx_hash": "0xpayout002a",
      "result": "Completed"
    },
    {
      "transaction_id": "9a8b7c6d-0002-4e5f-8a9b-000000000002",
      "amount": { "amount": "300.00", "token_id": "TRON_USDT", "chain_id": "TRON" },
      "tx_hash": null,
      "result": "Failed",
      "failed_reason": {
        "code": "transaction.rejected_by_policy",

  "commission_fees": [

  "failed_reason": {
    "code": "payment.payout_partially_failed",

In that case `failed_amounts` carries the amount but `transactions` has no matching entry, and the object-level `failed_reason` is the only explanation.

### An Off-Ramp payout is rejected by the bank

Confirm the account details with the recipient before resending. `requested_target` is a bank account, and `actual_payout_amount` would have been in the account's currency.

```json
{
  "data_type": "PaymentPayoutUpdate",
  "payout_id": "payout_004",
  "request_id": "request_payout_004",
  "source_account": "developer",
  "status": "RejectedByBank",
  "requested_amounts": [
    { "amount": "500.00", "token_id": "ETH_USDC", "chain_id": "ETH" }
  ],
  "failed_amounts": [
    { "amount": "500.00", "token_id": "ETH_USDC", "chain_id": "ETH" }
  ],
  "requested_target": {
    "target_type": "BankAccount",
    "bank_account_id": "ba_20260901_0007",
    "account_alias": "Vendor A operating account",
    "bank_name": "Example Bank",
    "currency": "USD"
  },
  "transactions": [],
  "actual_payout_amount": null,
  "initiator": "api_key_abc123",
  "commission_fees": [],
  "remark": null,
  "failed_reason": {
    "code": "transaction.rejected_by_bank",
    "message": "The receiving bank rejected this payout. Check the recipient's bank account details with them before resending — resending unchanged will most likely be rejected again."
  },
  "created_timestamp": 1744703000,
  "updated_timestamp": 1744703800
}
```

### Resending a failed payout

There is no retry on the original object. Create a new payout and keep the original `payout_id` in your own records so the two stay linked — the event does not carry a reference back to it.
