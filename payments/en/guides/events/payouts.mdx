These events track a single payout or transfer request, whether it settles in crypto or through an Off-Ramp to a bank account. Read [Events overview](/payments/en/guides/events/overview) first for the envelope, deduplication, and the rules that apply to every event.

For batch payouts, see [Bulk send events](/payments/en/guides/events/bulk-send).

## Events on this page

| Event | What it notifies you of | When you need it |
| --- | --- | --- |
| [`payment.payout.updated`](#payment-payout-updated) | A payout's result: in progress, completed, partially completed, failed, or rejected by the receiving bank. | Always — this is the event for payouts. |
| [`payment.bank_withdrawal.status.updated`](#payment-bank_withdrawal-status-updated) | A fiat withdrawal from one of your virtual accounts to a bank account changed status. | Required if you withdraw fiat. It is the only event for that flow. |

## `payment.payout.updated`

The primary payout event, identified by `payout_id`.

### Trigger conditions

**One event per change of this payout's `status`.** Progress inside the outgoing transactions — one completing, failing, or getting its `tx_hash` — is not notified separately.

| When you receive it | `status` | Final | What to do |
| --- | --- | --- | --- |
| The payout request is accepted | `Pending` | No | Record it and do not submit it again. |
| Fund preparation starts — consolidation, cross-chain conversion, commission | `Preparing` | No | Wait. |
| The outgoing transactions start executing | `Transferring` | No | Wait. Do not close the payment even if some outgoing transactions have completed. |
| Everything was paid out | `Completed` | Yes | Close the payout. This means Cobo completed the transfer, not that the recipient's platform has credited it. |
| Part of it did not go through | `PartiallyCompleted` | Yes | Send the amount in `failed_amounts` with a new payout. Do not resend the part that succeeded. |
| None of it went through | `Failed` | Yes | Read `failed_reason.code` and handle it. Do not retry in place. |
| The receiving bank returns the Off-Ramp transfer | `RejectedByBank` | No | Record the rejection, have your team check the recipient's bank details, and keep waiting for further events on this `payout_id`. |

<Warning>
  **`RejectedByBank` is not final.** After a rejection the payout can be retried against another bank account, returning to `Transferring` and possibly reaching `Completed`. Until it reaches `Completed`, `PartiallyCompleted`, or `Failed`: do not close the payment or mark it failed, do not create another payout to resend it (that double-pays), and do not treat the current `failed_reason` as the outcome.

  On recovery the same `status` appears again (a second `Transferring`, for example). **Deduplicate on `event_id`** — keying on `payout_id` plus `status` drops the recovery events.
</Warning>

### Event content

<div className="field-table">

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `data_type` | `string` | Required | Always `PaymentPayoutUpdate`. Use it to deserialize `data`. |
| `payout_id` | `string` | Required | The payout's identity, and the key you use when closing it and when raising a case. |
| `request_id` | `string` | Required | The request ID you supplied when creating the payout. |
| `source_account` | `string` | Required | Which account the money comes from: a merchant ID for a merchant account, or `developer`. |
| `status` | `string` | Required | The current payout status. See [Trigger conditions](#trigger-conditions) for the values. |
| `requested_target` | `object` | Required | Where the money is going, keyed by `target_type`: `Address` carries `address` and `chain_id`; `BankAccount` carries `bank_account_id`, `account_alias`, `bank_name`, and `currency`. It never carries full account details — look those up by `bank_account_id`. |
| `initiator` | `string` | Required | Who started the payout, usually an API key. |
| `remark` | `string` | Required | The note you wrote when creating the payout, returned as is. |
| `requested_amounts` | `array` | Required | **Source side**: what you asked to pay out, grouped by token and fixed at creation. |
| `failed_amounts` | `array` | Required | **Source side**: the part that was not paid out, in the same terms as `requested_amounts`; at a final status the amount that succeeded is the difference.<br/>• ⚠️ **Do not reconcile it against `transactions`** — a payout item can fail before any outgoing transaction exists (consolidation, cross-chain conversion, commission), leaving no matching entry. |
| `actual_payout_amounts` | `array` | Required | **Delivery side**: what the recipient actually received. **It has values only when `status` is `Completed` or `PartiallyCompleted`**, and is `[]` otherwise.<br/>• Read `amount_type` first: `Crypto` carries `token_id` and `chain_id`, with one entry per token actually sent; `Fiat` (Off-Ramp to a bank account) carries `currency` and is always a single entry.<br/>• ⚠️ **Do not subtract it from the source-side amounts** — conversion and fiat settlement mean the two sides are different assets. |
| `commission_fee` | `object` | Required | The commission Cobo charged, shaped `{ fee_amount }` and **denominated in USD**; `null` when none was charged. It is taken from Fee Station, whose balance is in USD, so it carries no token and stays a single total even across tokens. Reversals net off, so it can be `0` or negative. |
| `transactions` | `array` | Required | Every outgoing transaction for this payout, not the change since the last event; `[]` when there are none. Upsert by `transaction_id`, and **do not identify entries by `tx_hash`** — it is `null` before broadcast and cannot tell split transfers apart.<br/>• Each entry carries `transaction_id`, `amount`, `tx_hash`, and `result`, where `result` is `Completed`, `Failed`, or `null` when there is no result yet.<br/>• An entry with `result` `Failed` carries its own `failed_reason`.<br/>• ⚠️ After cross-chain conversion, an entry's `amount` is **in the token actually sent**, which can differ from the source token in `requested_amounts`. |
| `failed_reason` | `object` | Required | `{ code, message }` when `status` is `Failed`, `RejectedByBank`, or `PartiallyCompleted`; `null` otherwise. See [Failure reasons](#failure-reasons) for the values. |
| `created_timestamp` | `integer` | Required | When the payout was created, in Unix timestamp (seconds). |
| `updated_timestamp` | `integer` | Required | When the payout last changed status, in Unix timestamp (seconds). |

</div>

### Failure reasons

`failed_reason.code` is what you branch on. When a payout is partially completed, read the object-level `failed_reason` first — it is populated whatever stage the failure happened at, and if an outgoing transaction was the cause, the matching entry in `transactions` carries a more precise reason as well.

| `code` | What happened | What to do |
| --- | --- | --- |
| `payment.payout_partially_failed` | Some of the payout could not be completed. `failed_amounts` is the amount that did not go through. | Send that amount with a new payout. |
| `transaction.rejected_by_policy` | The transfer matched one of your own transaction policies. | Update that policy in Cobo Portal, then create the payout again. |
| `transaction.rejected_by_approval` | The transfer was rejected in your organization's approval process — by an approver, or by your callback server. | Confirm the reason with them, then create the payout again. |
| `transaction.rejected_by_signer` | The transfer was declined during signing by a co-signer. | Confirm the reason with the co-signer, then create the payout again. |
| `transaction.rejected_by_screening_app` | Your compliance team rejected the transfer in the [Screening App](https://manuals.cobo.com/en/apps/screening/introduction). | Review the case there, then create the payout again. |
| `payment.payout_fee_charge_failed` | The Fee Station balance is insufficient. | Add funds, then create the payout again. |
| `payment.payout_fee_station_not_configured` | Fee Station is not configured. | Configure it, then create the payout again. |
| `payment.payout_fee_charge_failed_unknown` | The fee could not be charged for another reason. | Check the Fee Station configuration and balance, then create the payout again. |
| `payment.payout_sweep_failed` | The sweep transaction that prepares the funds failed. | Create the payout again. |
| `payment.payout_bridge_failed` | Every cross-chain transaction failed, so the assets could not be converted. | Check that a route exists for the token pair, then create the payout again. |
| `payment.payout_transactions_failed` | Every outgoing transaction failed. The per-transaction reason is in `transactions`. | Read that detail before retrying. |
| `payment.payout_rejected_by_bank` | The receiving bank returned the transfer. Off-Ramp only. **This status is not final.** | Confirm the account details with the recipient and keep waiting for further events. Do not create another payout to resend it. |
| `transaction.rejected_by_compliance` | Cobo's compliance checks rejected the transfer. | Do not retry. Raise it with Cobo. |
| `transaction.failed` | The reason could not be classified. | Do not retry. Raise it with Cobo, quoting `payout_id`. |

### Sample events

Each sample shows the `data` object only. The envelope around it is the same for every event — see [Event structure](/payments/en/guides/events/overview#event-structure).

#### The payout is accepted

Record it and do not submit the request again. `requested_target` is your own instruction echoed back — check it against what you sent.

```json
{
  "data_type": "PaymentPayoutUpdate",
  "payout_id": "payout_001",
  "request_id": "request_payout_001",
  "source_account": "developer",
  "status": "Pending",
  "requested_amounts": [
    { "amount": "500", "token_id": "ETH_USDC", "chain_id": "ETH" }
  ],
  "failed_amounts": [],
  "requested_target": {
    "target_type": "Address",
    "address": "0xrecipient001",
    "chain_id": "ETH"
  },
  "transactions": [],
  "actual_payout_amounts": [],
  "initiator": "api_key_abc123",
  "commission_fee": null,
  "remark": "September vendor settlement",
  "failed_reason": null,
  "created_timestamp": 1744700000,
  "updated_timestamp": 1744700000
}
```

#### An Off-Ramp payout is rejected by the bank

**This is not a final status.** The on-chain leg has already completed (the entry in `transactions` is `Completed`); it is the receiving bank that returned the fiat credit, so `failed_amounts` is empty. Record the rejection, have your team confirm the account details with the recipient, and keep waiting for events on this `payout_id`: if the retry against another account succeeds, you receive a second `Transferring` and then `Completed`. Do not close the payment here, and do not create another payout.

```json
  },
  "transactions": [
    {
      "transaction_id": "9a8b7c6d-0004-4e5f-8a9b-000000000001",

  },

```

#### Resending a failed payout

There is no retry on the original object. Create a new payout and keep the original `payout_id` in your own records so the two stay linked — the event does not carry a reference back to it.

## `payment.bank_withdrawal.status.updated`

Fires when a bank withdrawal changes status. A bank withdrawal moves fiat out of one of your virtual accounts into a target bank account, and is created with [Create bank withdrawal](/payments/en/api-references/payment/create-bank-withdrawal).

| `status` | Meaning |
| --- | --- |
| `Pending` | The bank withdrawal was created and is awaiting processing. |
| `Processing` | The bank withdrawal is being processed. |
| `Completed` | The funds have left the virtual account. |
| `Failed` | The withdrawal failed. Read `failed_reason` for the cause. |

**Event content:** the `data` object carries `data_type` `PaymentBankWithdrawal`, plus:

- `bank_withdrawal_id` (required) — The bank withdrawal ID generated by Cobo.
- `request_id` (required) — The request ID you provided when creating the bank withdrawal.
- `source_bank_account_id` (required) — The ID of the source bank account, which must be a virtual account (tagged `VA`).
- `target_bank_account_id` (required) — The ID of the target bank account that receives the withdrawal.
- `source_bank_account` (required) — The full details of the source bank account.
- `target_bank_account` (required) — The full details of the target bank account.
- `currency` (required) — The fiat currency of the bank withdrawal, for example `USD`.
- `amount` (required) — The bank withdrawal amount, as a decimal string in the currency's display unit, for example `100.00`.
- `bank_tx_fee` (optional) — The bank transaction fee charged for the bank withdrawal.
- `status` (required) — The current status. One of: `Pending`, `Processing`, `Completed`, `Failed`.
- `remark` (optional) — The remark for the bank withdrawal.
- `failed_reason` (optional) — Why the bank withdrawal failed. Populated only when `status` is `Failed`.
- `timeline` (required) — The status timeline of the bank withdrawal. Each item carries a `status` and the `timestamp` at which the withdrawal entered it, in Unix timestamp (seconds).
- `created_timestamp` (required) — The creation time, in Unix timestamp (seconds).

<Note>
  The bank withdrawal payload does not carry an `updated_timestamp`. To determine when the withdrawal entered its current status, read the last entry in `timeline`.
</Note>

For full details, see [Get bank withdrawal information](/payments/en/api-references/payment/get-bank-withdrawal-by-id).
