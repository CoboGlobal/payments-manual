本页覆盖订单模式：每个收款订单有自己的收款地址、有效期和应收金额。请先阅读[事件概述](/payments/cn/guides/events/overview)了解外层结构、去重方式以及所有事件通用的规则。

## 本页的事件

| 事件 | 通知什么 | 什么时候需要订阅 |
| --- | --- | --- |
| [`payment.order.updated`](#payment-order-updated) | 一笔订单的收款结果：等待付款、某笔入金需要您处理、已付清、少付、过期，或订单结束后又收到钱。 | 必选——这是订单业务的事件。 |

## `payment.order.updated`

订单模式的主事件，以 `order_id` 标识。

**只有 `status` 为 `Completed` 时才能发货，不要自己比较金额。** 足额判定带容差（`amount_tolerance`），自行拿实收金额与应收金额比较，会把 Cobo 认定已付清的订单判成没付够。

### 事件触发条件

**订单 `status` 每变化一次发一条事件。** `status` 不变但某笔入金需要您知道时，也会发一条，用 `notice_type` 说明为什么。

| 什么时候会收到 | `status` | `notice_type` | 您该做什么 |
| --- | --- | --- | --- |
| 订单创建成功 | `Pending` | `null` | 建立订单记录，向付款方展示应付金额。 |
| 检测到该订单的**第一笔**入金 | `Processing` | `null` | 更新进度，不要发货。 |
| 某笔入金进入 `ActionRequired` | `Processing` | `PaymentUpdated` | 按该条目的 `message` 处理，这笔资金在您处理前一直挂起。 |
| 某笔入金失败 | `Processing` | `PaymentFailed` | 读该条目的 `failed_reason.code`。这笔钱进不了订单，按您自己的规则联系付款方重付。 |
| 累计实收达到足额阈值。多付也走这一条，没有 `Overpaid` 状态 | `Completed` | `null` | 发货，以 `order_id` 作为幂等键。 |
| 有效期结束那一刻有已完成入账，但未达阈值 | `Underpaid` | `null` | 进入少付处理，不要按足额订单发货。 |
| 有效期结束那一刻没有任何已完成入账，或订单被撤销 | `Expired` | `null` | 关闭付款窗口。需要继续收款时创建新订单。 |
| 订单已是终态，又收到一笔入金**且该笔通过筛查** | 保持原终态 | `LatePaymentReceived` | 人工决定退款还是补发，不要重开原订单。 |
| 订单已是终态，晚到的那笔**筛查未通过** | 保持原终态 | `PaymentFailed` | 不需要处理，这笔钱没有到账。 |

**终态在有效期结束那一刻定下来，之后不再重算。** 因此您可能看到 `status` 为 `Expired`、`credited_amount` 为 `0`，而 `transactions` 里有一条 `Completed`——那是到期之后才到的钱（`is_late` 为 `true`），不参与终态判定，也不计入 `credited_amount`。

**这些情况不发事件**：检测到第二笔及以后的入金、入金进入筛查、入金顺利通过筛查（`credited_amount` 会变但不通知）、晚到款刚到达还没走完筛查。

### 事件内容

<div className="field-table">

| 字段 | 类型 | 必填性 | 说明 |
| --- | --- | --- | --- |
| `data_type` | `string` | 必填 | 固定为 `PaymentOrderUpdate`，用于反序列化 `data`。 |
| `order_id` | `string` | 必填 | 订单身份，也是您做发货幂等时使用的键。 |
| `psp_order_code` | `string` | 必填 | 您自己为该订单分配的参考编号。 |
| `merchant_order_code` | `string` | 必填 | 订单归属商户时，商户自己的参考编号，否则为 `null`。 |
| `merchant_id` | `string` | 必填 | 订单归属商户时，该商户的 ID，否则为 `null`。 |
| `receive_address` | `string` | 必填 | 付款方转账的目标地址。 |
| `expired_at` | `integer` | 必填 | 付款窗口关闭时间，Unix 时间戳（秒）。 |
| `status` | `string` | 必填 | 订单当前状态，取值与含义见[事件触发条件](#事件触发条件)。 |
| `notice_type` | `string` | 必填 | `status` 没变但仍通知您的原因，取 `PaymentUpdated`、`PaymentFailed` 或 `LatePaymentReceived`；其余情况为 `null`。 |
| `requested_amount` | `object` | 必填 | 订单应收总额，**含您的手续费**，创建时确定、之后不变。展示给付款方用。<br/>• ⚠️ **它不是发货阈值**：足额判定带容差，能否发货以 `status` 为 `Completed` 为准。 |
| `credited_amount` | `object` | 必填 | 已收到并计入订单的总额，订单对账以它为准。<br/>• **它不包含**：还在筛查中的入金、等您处理的入金、被拒绝的入金，以及订单结束后才到的晚付（条目 `is_late` 为 `true`）。<br/>• ⚠️ **不要自己对 `transactions` 求和**，晚到款会让您的和偏大。<br/>• ⚠️ 它**含将要分给您的手续费，不是商户的入账金额**。两个账户各自实际收到多少，看[余额变动](/payments/cn/guides/events/balances)。 |
| `outstanding_amount` | `object` | 必填 | **付款方还需再付多少**＝`requested_amount` − `credited_amount`。<br/>• `requested_amount` 在查询接口里叫 `payable_amount`，所以也可以记成「应付 − 已收」。<br/>• **怎么用：`status` 为 `Underpaid` 时用它告诉付款方还差多少。**<br/>• ⚠️ **不要用它判断是否少付**：`status` 为 `Completed` 时它仍可能大于 `0`（在 `amount_tolerance` 容差内完成），此时订单是足额的，按它催款会催一笔不该催的钱。是否少付只看 `status`。<br/>• 下限为 `0`，多付时保持 `0`，**无法表达多收了多少**。 |
| `transactions` | `array` | 必填 | 该订单**至今的全部入金**，不是增量；无入金时为 `[]`。请整体替换本地副本，按 `transaction_id` upsert。<br/>• 每个条目含 `transaction_id`、`tx_hash`、`amount`、`source_address`、`is_late`，以及条目自己的 `status`（五个取值与充值相同）、`screening_mode`、`message`、`failed_reason`。<br/>• `is_late` 为 `true` 表示这笔钱在订单终态之后才到，不计入 `credited_amount`。<br/>• ⚠️ **低于粉尘阈值的入金不在数组里**，默认阈值为 `0.05`，各 token 的阈值见登记入金地址接口返回的 `min_amount`。 |
| `created_timestamp` / `updated_timestamp` | `integer` | 必填 | 该订单的创建时间与**最近一次状态更新时间**，Unix 时间戳（秒）。它们描述的是对象，不是这条事件何时产生——那是外层的 `created_timestamp`，单位毫秒。用 `updated_timestamp` 丢弃乱序到达的旧事件。 |

</div>

订单对象本身没有 `failed_reason`。订单不会「失败」，只会过期或少付；失败属于 `transactions` 里的某一笔入金。

所有金额固定 2 位小数、去掉尾零。应付类金额本来就不超过 2 位，链上实收金额（`credited_amount`、条目的 `amount`）按 `ROUND_DOWN` 截断——付款方打 `103.0305`，事件里是 `103.03`。足额判定用的是未截断的原值，`status` 不受影响。

### 失败原因

`failed_reason.code` 是您分支的依据。`transactions` 中的条目只可能携带下面三个。提交问题时要提供的 ID 是 `order_id`，不是条目的 `transaction_id`。

| `code` | 发生了什么 | 怎么处理 |
| --- | --- | --- |
| `transaction.rejected_by_screening_app` | 您自己的合规团队在 [Screening App](https://manuals.cobo.com/cn/apps/screening/introduction) 中拒绝了这笔入金。 | 到该应用查看原因。 |
| `transaction.rejected_by_compliance` | Cobo 的合规检查拒绝了这笔入金。 | 与 Cobo 确认。 |
| `transaction.failed` | 其余全部情况，包括链上失败，以及因链重组而被回滚的入金。 | 提交问题并提供下面这个 ID。 |

### 示例事件

以下示例只展示 `data` 对象。外层结构所有事件都一样，参见[事件结构](/payments/cn/guides/events/overview#事件结构)。

#### 订单已创建

向付款方展示应付金额。`transactions` 为空，两个依赖到账的金额均为 `0`。

```json
{
  "data_type": "PaymentOrderUpdate",
  "order_id": "order_001",
  "psp_order_code": "psp_order_001",
  "merchant_id": "M1001",
  "merchant_order_code": "shop_20260921_0001",
  "status": "Pending",
  "notice_type": null,
  "receive_address": "0xorder_addr_001",
  "expired_at": 1744692600,
  "requested_amount": { "amount": "102", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "credited_amount": { "amount": "0", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "outstanding_amount": { "amount": "102", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "transactions": [],
  "created_timestamp": 1744689000,
  "updated_timestamp": 1744689000
}
```
