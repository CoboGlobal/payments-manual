本页覆盖订单模式：每个收款订单有自己的收款地址、有效期和应收金额。请先阅读[事件概述](/payments/cn/guides/events/overview)了解外层结构、去重方式以及所有事件通用的规则。

## 本页的事件

| 事件 | 通知什么 | 什么时候需要订阅 |
| --- | --- | --- |
| [`payment.order.updated`](#payment-order-updated) | 一笔订单的收款结果：等待付款、某笔入金需要您处理、已付清、少付、过期，或订单结束后又收到钱。 | 必选——这是订单业务的事件。 |

## `payment.order.updated`

订单模式的主事件，以 `order_id` 标识。

**只有 `status` 为 `Completed` 时才能发货，不要自己比较金额。** 足额判定带容差（`amount_tolerance`），自行拿实收金额与应收金额比较，会把 Cobo 认定已付清的订单判成没付够。

### 事件触发条件

**订单 `status` 每变化一次发一条事件。** `status` 不变但您仍需要处理时，也会发一条，用 `notice_type` 说明为什么。除此之外不发——包括订单在 `Processing` 期间入金反复变化，见下方。

| 什么时候会收到 | `status` | `notice_type` | 您该做什么 |
| --- | --- | --- | --- |
| 订单创建成功 | `Pending` | 无 | 建立订单记录，向付款方展示应付金额。 |
| 检测到该订单的**第一笔**入金，订单从 `Pending` 变为 `Processing` | `Processing` | 无 | 更新进度，不要发货。 |
| 某笔入金进入 `ActionRequired`，**订单状态不变** | `Processing` | `PaymentUpdated` | 按该条目的 `message` 处理，这笔资金在您处理前会一直挂起。 |
| 累计实收达到足额阈值，订单变为 `Completed`。多付也走这一条，没有 `Overpaid` 状态 | `Completed` | 无 | 发货，以 `order_id` 作为幂等键。 |
| 有效期结束，存在已完成入账但未达阈值 | `Underpaid` | 无 | 进入少付处理，不要按足额订单发货。 |
| 有效期结束且没有任何已完成入账，或订单被撤销 | `Expired` | 无 | 关闭付款窗口。需要继续收款时创建新订单。 |
| 订单已是终态，又收到一笔入金**且该笔通过筛查**，**订单状态保持终态** | 保持原终态 | `LatePaymentReceived` | 人工决定退款还是补发，不要重开原订单。 |

### 事件内容

| 字段 | 说明 |
| --- | --- |
| `order_id` | 订单身份，也是您做发货幂等时使用的键。 |
| `psp_order_code` | 您自己为该订单分配的参考编号。 |
| `merchant_order_code` | 订单归属商户时，商户自己的参考编号。 |
| `receive_address` | 付款方转账的目标地址。 |
| `expired_at` | 付款窗口关闭时间，Unix 时间戳（秒）。 |
| `notice_type` | `status` 没变但仍通知您的原因，取 `PaymentUpdated` 或 `LatePaymentReceived`。 |
| `transactions` | 该订单至今关联的全部入金，参见[读取入金数组](#事件内容)。 |

订单对象本身没有 `failed_reason`。订单不会「失败」，只会过期或少付；失败属于 `transactions` 里的某一笔入金。

**三个金额字段怎么用。**

| 字段 | 是什么 | 怎么用 |
| --- | --- | --- |
| `requested_amount` | 订单应收总额，**含您的手续费**。 | 展示给付款方。它不是发货阈值。 |
| `credited_amount` | 已收到并计入订单的总额。 | 用于对账。不要自己对数组求和：晚到款是 `Completed` 条目但不计入订单，自行求和会偏大。 |
| `outstanding_amount` | 还差多少未收到。 | 用于告知付款方还需支付多少。 |

`credited_amount` 包含将要分给您的那部分手续费，因此它不是商户的入账金额。两个账户各自实际收到多少，请读取 `payment.account.balance.updated`，或调用 `GET /payments/balance_changes?source_id=<order_id>`。

`outstanding_amount` 下限为 `0`，多付时保持 `0`，因此它无法表达多收了多少。它还把四种情况合并成一个数：付款方没打钱、资金在筛查中、资金在等您补充信息、资金被拒绝。这四种的处理方式完全不同，需要遍历 `transactions` 并按条目的 `status` 分组，才能知道钱卡在哪里。

**读取 `transactions` 数组。**

`transactions` 是该订单当前的完整入金列表，不是自上条事件以来的增量。请整体替换本地副本，并按 `transaction_id` 做 upsert。

每个条目包含 `transaction_id`、`tx_hash`、`amount`、`source_address`、`is_late`，以及该条目自己的 `status`，取值与充值相同的五个。处于 `PendingScreening` 或 `ActionRequired` 的条目还带 `screening_mode`，`ActionRequired` 的条目还带 `message`。失败的条目带自己的 `failed_reason`，见[失败 code](#失败原因)。

低于粉尘阈值的入金完全不会出现在数组里。默认阈值为 `0.05`，金额需严格大于该值才会保留。

### 失败原因

`failed_reason.code` 是您分支的依据。`transactions` 中的条目只可能携带下面三个。提交问题时要提供的 ID 是 `order_id`，不是条目的 `transaction_id`。

| `code` | 发生了什么 | 怎么处理 |
| --- | --- | --- |
| `transaction.rejected_by_screening_app` | 您自己的合规团队在 [Screening App](https://manuals.cobo.com/cn/apps/screening/introduction) 中拒绝了这笔入金。 | 到该应用查看原因。 |
| `transaction.rejected_by_compliance` | Cobo 的合规检查拒绝了这笔入金。 | 与 Cobo 确认。 |
| `transaction.failed` | 其余全部情况，包括链上失败，以及因链重组而被回滚的入金。 | 提交问题并提供下面这个 ID。 |

### 示例事件

以下示例只展示 `data` 对象。外层结构所有事件都一样，参见[事件结构](/payments/cn/guides/events/overview#事件结构)。

#### 订单已创建

向付款方展示应付金额。`transactions` 为空，两个依赖到账的金额均为 `0`。

```json
{
  "data_type": "PaymentOrderUpdate",
  "order_id": "order_001",
  "psp_order_code": "psp_order_001",
  "merchant_id": "M1001",
  "merchant_order_code": "shop_20260921_0001",
  "status": "Pending",
  "receive_address": "0xorder_addr_001",
  "expired_at": 1744692600,
  "requested_amount": { "amount": "102.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "credited_amount": { "amount": "0", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "outstanding_amount": { "amount": "102.00", "token_id": "ETH_USDC", "chain_id": "ETH" },
  "transactions": [],
  "created_timestamp": 1744689000,
  "updated_timestamp": 1744689000
}
```

#### 不会发事件的情况

下面这些会改变订单的内容，但不产生通知，因为订单 `status` 没有变化，也不需要您采取任何处理：

- 检测到第二笔及以后的入金。
- 某笔入金进入筛查。
- **某笔入金通过筛查**，这会抬高 `credited_amount`、降低 `outstanding_amount`。
- 某笔入金失败。
- 晚到款已到达但尚未通过筛查。
