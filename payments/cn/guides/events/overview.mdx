Cobo Payments 通过 Webhook 事件通知您的系统。本章按支付业务组织：找到与您业务对应的页面，该页面会列出这条链路所需的全部事件。

## 事件结构

所有 Webhook 消息共用同一个外层结构。先用 `type` 路由，再按 `data_type` 反序列化 `data`。

外层的 `created_timestamp` 是 **Webhook 服务收到这条事件的时间，单位毫秒**，重投时不变；投递链路可能打乱顺序，所以**不要用它判断事件先后**。`data` 里的 `created_timestamp` 与 `updated_timestamp` 是**业务对象自己的创建与最近更新时间，单位秒**，判断先后用后者。

外层的 `status`（`Success`、`Retrying`、`Failed`）以及重试时才出现的 `next_retry_timestamp`、`retries_left` 描述的是这条消息的投递情况，与业务无关，处理时可以忽略。

```json
{
  "event_id": "8f2e919a-6a7b-4a9b-8c1a-4c0b3f5b8b2f",
  "url": "https://example.com/webhook",
  "created_timestamp": 1701396866000,
  "type": "payment.topup.updated",
  "data": { "data_type": "PaymentTopUpUpdate" },
  "status": "Success"
}
```

| `type` | `data.data_type` | 业务单据 ID |
| --- | --- | --- |
| `payment.topup.updated` | `PaymentTopUpUpdate` | `transaction_id` |
| `payment.order.updated` | `PaymentOrderUpdate` | `order_id` |
| `payment.refund.updated` | `PaymentRefundUpdate` | `refund_id` |
| `payment.payout.updated` | `PaymentPayoutUpdate` | `payout_id` |
| `payment.bulk_send.updated` | `PaymentBulkSendUpdate` | `bulk_send_id` |
| `payment.bulk_send.item.updated` | `PaymentBulkSendItemUpdate` | `bulk_send_item_id` |

充值没有单独的 `topup_id`。它的对象 ID 就是 `transaction_id`，因为一笔充值本身就是一笔入账交易。

## 在两个层面做去重

| ID | 防的是什么 |
| --- | --- |
| `event_id` | 重复投递。同一条消息重投时 `event_id` 不变。**去重只能用它**——同一个 `status` 可能合法地出现两次，例如转出被银行退回后换账户重试，会再来一条 `Transferring`。 |
| 业务单据 ID | 同一个业务事实被不同事件或不同代码路径处理两次。 |

两层都要做。对 `event_id` 建唯一约束用于投递去重，再对每个不可逆动作（入账、发货、关闭付款）按业务单据 ID 建第二个唯一约束。

## 所有事件通用的规则

**按 `status` 分支。** 它是唯一供程序判断使用的字段。

- 不要自己比较金额来判断订单是否付清。订单足额判定带容差，自行比较会把 Cobo 认定已付清的订单判成没付够。
- 不要匹配 `message` 或 `failed_reason.message`。这些文本面向运营人员，措辞会变。
- 不要用链上确认数判断资金是否可用。确认数是否达标已经体现在 `status` 里。

**数组是全量快照。** `transactions` 等字段携带的是该对象当前的完整列表，不是自上条事件以来的增量。请整体替换本地副本，不要往里追加。

**投递不保证顺序。** 按业务单据 ID 做 upsert，用 `data.updated_timestamp` 判断先后：**严格小于本地值才丢弃，相等的不能丢**（精度只到秒，同一秒内可能有多条内容不同的事件）。终态不能被后到的处理中事件回退。

**用每条事件的 `status` 覆盖本地状态，不要校验状态迁移是否合法。** 中间状态可能没有对应的事件（例如一笔入金从 `Detected` 直接到 `Completed`），那不是丢事件。需要您动手的状态不会被跳过。

**字段始终存在，不适用时为 `null`。** 各页字段表中的字段都会出现在 payload 里，标注「选填」或「仅……时出现」的除外。例如 `failed_reason` 只有失败时有值，其余情况是 `null` 而不是没有这个键；数组字段为空时是 `[]`。请按 `null` 处理，不要用「有没有这个键」判断。

## 读取失败原因

可能汇报失败的事件会携带一个 `failed_reason` 对象。

```json
"failed_reason": { "code": "transaction.rejected_by_policy", "message": "..." }
```

`code` 是受控枚举，也是您分支的依据。请保留完整字符串，不要按点号拆开——前缀是取值的一部分，不是需要您解读的信息。

`message` 面向运营人员，措辞可能调整，因此可以展示但绝不能用于匹配。

每个业务页面会列出该对象上可能出现的 code，并按需要采取的处理方式分组：[充值](/payments/cn/guides/events/top-up#失败原因)、[订单](/payments/cn/guides/events/orders#失败原因)、[退款](/payments/cn/guides/events/refunds#失败原因)、[资金转出](/payments/cn/guides/events/payouts#失败原因)、[批量下发](/payments/cn/guides/events/bulk-send#批次的失败原因)。

### 提交问题时报业务单据 ID

需要排查失败时，请提供业务单据 ID 而不是交易 ID：充值用 `transaction_id`，其余用 `order_id`、`refund_id`、`payout_id`、`bulk_send_id`、`bulk_send_item_id`。每个 payload 都一定带自己的单据 ID，而交易 ID 在退款和批量下发条目的 payload 中根本不存在。

对于 Payout，一个 `payout_id` 下可能有多笔转出交易，因此只有单据 ID 才能追溯整个请求。

## 读取金额

所有金额都是十进制字符串而不是数字类型，请使用 decimal 类型解析。

| 结构 | 字段 | 用在哪 |
| --- | --- | --- |
| 资产金额 | `amount`、`token_id`、`chain_id` | 绝大多数金额字段。 |
| 资产或法币金额 | `amount_type`，以及 `amount` 加上 `token_id` 与 `chain_id`，或者 `currency` | 可能是加密货币也可能是法币的字段，例如 `actual_payout_amounts` 的元素。请先读 `amount_type`，不要根据有没有 `token_id` 推断。 |
| 佣金 | `fee_amount` | Cobo 收取的佣金，**单位为美元**。佣金从 Fee Station 扣，余额是美元口径，所以不带币种。 |

```json
{ "amount": "100", "token_id": "ETH_USDC", "chain_id": "ETH" }
{ "amount_type": "Crypto", "amount": "300", "token_id": "TRON_USDT", "chain_id": "TRON" }
{ "amount_type": "Fiat", "amount": "497.5", "currency": "USD" }
{ "fee_amount": "2.5" }
```

字段名为复数的（例如 `requested_amounts`）是数组，可能跨多种 token；单数字段是单个对象，只涉及一种资产。不要跨资产相加。数组按 `token_id` 分组，同一种币在两条链上是两项。

**金额固定 2 位小数，去掉尾零**（`100.00` 输出 `100`）。应付类金额本来就不超过 2 位；链上实收金额按 `ROUND_DOWN` 截断，因此可能比链上的实际数值少几位。

Webhook 消息不携带余额和手续费明细，以保证您读到的数值不会因为并发活动而失真。要保持自己账本的实时性，请在收到事件时调用 [List merchant balances](/payments/en/api-references/payment/list-merchant-balances) 或 [Get developer balances](/payments/en/api-references/payment/get-developer-balance)。需要手续费明细时，请使用交易查询接口或 [Generate reports](/payments/en/api-references/payment/generate-reports)。
